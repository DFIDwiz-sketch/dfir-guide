## 목표와 준비물

계정 하나의 인증과 권한 사용을 **원래 클라이언트 → 검증·티켓 발급 DC → 실제 서비스 대상**에서 확인합니다. AD 구성도, 계정·장비 식별자, 조사 기간과 각 위치의 로그가 필요합니다. [가상 로그 실습](first-investigation.html)으로 NTLM 사례를 먼저 연습할 수 있습니다.

AD는 사용자 목록뿐 아니라 컴퓨터, 그룹, 서비스 계정, 정책과 객체 권한을 연결하는 환경입니다. 인증 성공과 자원 접근 허용은 다른 판단입니다.

## 1단계 — 계정과 장비 식별표 만들기

| 항목 | 기록할 내용 |
| --- | --- |
| 계정 | 도메인·이름·SID, 사용자/서비스/컴퓨터 구분 |
| 원래 클라이언트 | 장비 이름, 해당 시점 주소와 사용자 |
| 대상 서비스 | 장비·서비스·접근 주소와 역할 |
| DC | 검증 또는 티켓 발급을 관찰한 DC |
| 기준 시간 | 원문 시간대, 조사 시작·끝과 시계 오차 |

같은 이름의 로컬 계정과 도메인 계정을 구분하고 이름 변경이 의심되면 SID 등 식별자를 확인합니다. 컴퓨터 계정 이름 끝의 `$`처럼 형태가 힌트가 될 수 있지만 이름만으로 소유자와 권한을 확정하지 않습니다.

## 2단계 — 실제 인증 프로토콜 확인하기

대상의 4624·4625에서 인증 패키지와 로그온 유형을 확인합니다. NTLM이면 해당 검증 장비의 4776, Kerberos이면 관련 DC의 4768·4769 등을 비교합니다. 앱 설정에 Negotiate가 있다는 사실만으로 Kerberos 사용을 확정하지 않습니다.

**가상 자료 연습:** E003은 DC의 검증, E004는 파일 서버의 로그온입니다. 4776의 Workstation 값만으로 실제 서비스 대상을 모두 알 수 없으므로 E004와 네트워크 자료가 필요합니다.

## 3단계 — 인증과 권한을 따로 조사하기

인증된 계정이 대상에서 어떤 권한을 가졌는지 확인합니다. 사용자 이름이 관리자처럼 보이거나 특정 그룹에 속했다는 이유만으로 모든 접근 권한을 가졌다고 가정하지 않습니다.

| 권한 영역 | 비교할 자료 |
| --- | --- |
| 파일 공유 | 공유 권한과 파일 시스템 ACL |
| 로컬 관리 | 대상의 그룹·보안 정책과 실제 로그온 문맥 |
| AD 객체 | 해당 객체 ACL, 위임과 변경 가능한 속성 |
| 서비스·앱 | 서비스 계정, 앱 자체의 역할·접근 제어 |

현재 그룹과 ACL은 조사 시점의 상태입니다. 사건 당시 권한을 설명하려면 변경 이벤트·구성 이력·백업을 함께 확인합니다. 그룹 중첩과 세션·토큰의 갱신 시점도 고려합니다.

## 4단계 — 로그온 뒤의 변경 찾기

대상 서버의 프로세스·서비스·예약 작업과 파일 접근 자료를 확인합니다. AD 변경은 어떤 객체가 누구에 의해 변경됐는지 원문으로 확인합니다.

| 예시 이벤트 | 조사 목적 | 선행 조건·주의 |
| --- | --- | --- |
| 4720 | 사용자 계정 생성 | 해당 감사와 로그 보존 |
| 4728 / 4732 / 4756 | 보안 그룹 구성원 추가 | 글로벌·로컬·유니버설 그룹의 맥락 구분 |
| 5136 | 디렉터리 서비스 객체 변경 | 관련 감사 정책 및 객체 SACL 설정 필요 |
| 4698 / 4702 | 대상 장비의 작업 생성·변경 | 작업 XML과 실제 실행은 별도 확인 |

이 목록은 조사 출발점입니다. 하나의 변경 이벤트만으로 전체 이전·이후 상태를 모두 알 수는 없습니다. 누락된 감사 조건은 조사 한계로 적습니다.

## 5단계 — 계정과 대상의 범위 넓히기

확인한 계정이 다른 서버에도 접근했는지, 동일 출발지가 다른 계정을 사용했는지 찾습니다. 실패·성공, 실제 변경·실행을 나눠 기록합니다. 공용 관리 서버의 활동은 여러 정상 작업이 섞일 수 있습니다.

가상 자료 E010~E011은 앞선 성공과 다른 계정·출발지의 실패입니다. 시각이 가깝다는 이유로 같은 사용자의 연속 동작이라고 합치지 않습니다. Logon ID는 장비와 부팅 맥락 없이 전역으로 조인하지 않습니다.

## 6단계 — 대응 대상과 재검증 항목 정하기

계정 악용이 확인되면 계정·세션·변경 객체·관련 장비를 함께 검토합니다. 비밀번호만 바꾸고 새로 생긴 작업이나 권한 변경을 남겨두지 않도록 범위를 확인합니다. 반대로 근거가 부족한 정상 관리 활동을 일괄 차단하지 않도록 업무 담당자와 승인 내역을 비교합니다.

도메인 핵심 키나 DC 침해가 의심되면 개별 사용자 비밀번호 변경 수준을 넘어 조직의 AD 복구 절차로 전환합니다. 이 입문 가이드의 일반 조치만으로 도메인 복구 완료를 선언하지 않습니다.

## 결과 기록과 완료 기준

```text
계정 식별자와 유형:
원래 클라이언트 / DC / 대상 서비스:
확인된 인증과 근거 이벤트:
사건 당시 권한을 설명하는 자료:
인증 이후 확인된 변경·실행:
다른 대상·계정으로의 범위:
미확인 항목과 추가 수집:
```

계정 신원, 실제 인증 방식, 권한과 후속 행동을 각각 근거로 설명하면 이 단계가 끝납니다. 다음은 [NTLM 조사](ntlm-triage.html) 또는 [침해사고 대응](incident-triage.html)입니다.
