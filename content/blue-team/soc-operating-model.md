## 목표와 준비물

SOC(Security Operations Center)는 탐지·조사·대응을 수행하는 운영 체계입니다. 항상 별도의 방이나 24시간 전담팀이 필요한 것은 아닙니다. 작은 팀도 업무 범위와 인계를 명확히 해야 경보가 담당자 없이 남지 않습니다.

준비물은 자산·서비스 담당 목록, 현재 경보와 수집 경로, 사고 대응 책임자입니다. 아래 역할표와 시간 기준은 **이 사이트의 운영 설계 예시**이며 NIST가 정한 직급이나 공통 SLA가 아닙니다.

## 1단계 — 보호할 업무와 운영 범위 정의하기

조직의 핵심 업무 3개를 적고 서비스·계정·데이터·외부 공급자에 연결합니다. 운영 범위에는 업무 시간과 비업무 시간, 제외된 네트워크, 지원하지 않는 장비, 조사를 요청할 수 있는 대상을 포함합니다.

예: ‘PCTE 가상 네트워크의 네트워크 수집을 관측하고, 지정 Windows 장비의 Hunt를 요청할 수 있다.’ 이는 SaaS 메일과 물리적 장비까지 관측한다는 뜻이 아닙니다. 외부 침해 제보를 받을 경로도 정합니다.

**확인:** 경보의 대상 자산에 소유자와 업무 중요도가 붙는지 봅니다. 자산 소유자가 없으면 대응 작업의 담당을 임시 지정하고 해결 과제로 남깁니다.

## 2단계 — 도구와 실제 책임을 연결하기

| 역할 | 책임 | 분석가에게 제공할 내용 |
| --- | --- | --- |
| 분류 담당 | 원문 확인·긴급성·중복·담당 배정 | 근거 이벤트와 미확인 사항 |
| 조사·헌팅 담당 | 타임라인·범위·가설 검증 | 재현 검색, 추가 수집 계획 |
| 수집·플랫폼 담당 | 입력·파서·보존·접근 권한 | 원본 위치와 수집 장애 상태 |
| 서비스·신원 담당 | 업무 영향 확인·격리·권한 처리 | 조치 시각·결과·의존성 |
| 사고 책임자 | 우선순위·공동 대응·복구 판단 | 의사결정 근거와 남은 위험 |
| 탐지 담당 | 규칙 변경·정상 사례·회귀 검증 | 변경 이력과 검증 범위 |

한 사람이 여러 역할을 맡을 수 있습니다. Tier 1·2·3 명칭은 조직마다 다르므로 번호만으로 업무를 추측하지 않습니다. 클라우드나 공급망 사건은 신원·개발·백업 담당이 함께 참여할 조건을 정합니다.

## 3단계 — 조치 권한과 연락 경로를 사전에 정하기

Hunt 실행, 원본 내보내기, EDR 격리, 방화벽 변경, 계정 제한과 서비스 재시작을 각각 누가 실행할 수 있는지 기록합니다. 사용 권한이 있다고 모든 대상에서 조치해도 되는 것은 아닙니다. 운영 범위와 사전 승인된 절차를 연결합니다.

각 조치에 대상 확인 방법, 영향·되돌리기, 성공 검증을 붙입니다. 격리 요청이 접수됐다는 기록과 실제 연결이 제한된 결과를 따로 확인합니다. 비상 연락 실패 때 대체 담당과 인계 조건도 정합니다.

**실습:** 특정 서비스 계정이 의심받았다고 가정합니다. 즉시 비밀번호 변경 전 확인할 정상 작업·의존성, 조치 담당, 세션·토큰·권한 조사 항목을 적습니다.

## 4단계 — 교대와 미완료 업무 인계하기

```text
사건 ID / 우선순위 / 다음 담당:
최근 확인된 사실과 근거 링크:
수행한 조치 / 시각 / 실제 결과:
미수집·보존 만료 자료:
다음 행동 / 담당 / 기한:
긴급 재연락 조건:
```

다음 담당이 기록을 받았는지 확인하고, 인계 직후 수행할 한 가지 행동을 명확히 합니다. 아직 확인할 것이 남았는데 ‘이상 없음’만 쓰면 조사 맥락이 사라집니다. 보존 만료가 임박한 자료는 별도 강조합니다.

## 5단계 — 운영 지표의 시점을 정의하기

| 지표 예시 | 시점·분모 정의 | 함께 볼 제한 |
| --- | --- | --- |
| 분류 대기시간 | 경보 생성부터 첫 분류 시작까지 | 비업무 시간·백필 자료 구분 |
| 억제 실행시간 | 억제 결정부터 결과 검증까지 | 요청 완료와 조치 성공 분리 |
| 미완료 경보 나이 | 현재 시각에서 생성 시각을 뺀 값 | 중복·인계·외부 대기 상태 |
| 필수 로그 확인율 | 기대 source 중 정상 시험을 통과한 수 / 전체 기대 수 | 검색 결과에 없는 source도 포함 |
| 규칙 재검증 통과율 | 시험한 규칙 중 정해진 조건을 통과한 수 / 시험한 규칙 수 | 미시험 규칙과 데이터 부재 별도 |
| 경보 정확도 | 분류가 끝난 후보 중 목적에 맞는 후보의 비율 | 실제 악성과 규칙 일치를 구분 |

MTTD·MTTR을 사용할 경우 시작·종료 시점을 명시합니다. 실제 침해 시작을 모르면 ‘침해부터 탐지까지’라는 값을 계산하지 않습니다. 평균 하나보다 중앙값·상위 지연·사건별 설명을 함께 봅니다. 경보를 빨리 닫는 것이 조사 품질의 증거는 아닙니다.

## 6단계 — 분석가 부담과 반복 작업 개선하기

같은 source 장애 경보가 반복된다면 규칙의 문자열을 바꾸기 전에 수집 원인을 고칩니다. 넓은 예외로 경보를 숨기지 않고 대상·만료·정상 근거를 정합니다. 특정 분석가에게만 지식이 몰리면 짧은 원문 확인 가이드와 인계 연습으로 분산합니다.

반복 업무 자동화는 [SOAR·AI 운영](soar-ai-operations.html)을 따릅니다. AI 요약이 있어도 원문과 근거 ID를 검토할 사람이 필요합니다. 호출 실패·품질 문제를 개인의 처리 속도 문제로만 평가하지 않습니다.

## 7단계 — 짧은 운영 점검으로 개선 과제 만들기

매 운영 점검에서 오래된 미완료 사건, 끊긴 필수 source, 만료할 예외, 최근 실패한 검증을 확인합니다. 각 문제를 담당·기한·완료 증거가 있는 작업으로 바꿉니다. 실제 침해 중인 경우 정기 점검을 기다리지 않습니다.

**완료 기준:** 한 사건의 조사·조치·인계 책임을 설명하고, 대기와 실패를 숨기지 않는 지표를 만들 수 있습니다. 다음은 [관측 지도](defensible-visibility.html)입니다.
