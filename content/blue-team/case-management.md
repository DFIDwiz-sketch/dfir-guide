## 목표와 준비물

사건 관리 시스템은 누가 무엇을 확인했고 어떤 조치가 남았는지 보존합니다. Splunk는 검색, Arkime는 세션·패킷, Velociraptor는 호스트 수집에 활용하고 사건 기록에는 각 근거로 이동할 수 있는 연결을 둡니다. 시스템마다 저장한 사실의 역할이 다릅니다.

TheHive가 있으면 현재 버전의 Case·Alert·Observable·Task를 사용합니다. 없으면 동일 항목을 문서·티켓으로 기록합니다. 2022년 화면을 현재 설치 절차로 그대로 사용하지 않습니다. 기능·권한·라이선스는 사용 버전의 공식 문서에서 확인합니다.

## 1단계 — 사건의 범위와 ID 만들기

새 조사에 ID·제목·작성 시각·담당·대상·우선순위 근거를 적습니다. 제목은 ‘LAB-FS01 작업 생성·변경 검토’처럼 관찰에 맞춥니다. 아직 확인되지 않은 공격자·유출·침해 확정을 제목에 넣지 않습니다.

이 과정의 예시는 `LAB-CASE-001`입니다. 같은 조사를 이미 진행 중이라면 근거를 기존 사건에 연결합니다. 같은 IP만으로 합치지 말고 자산·계정·기간·행동과 기존 범위를 비교합니다.

## 2단계 — 경보와 사건을 연결하기

TheHive의 현재 공식 문서는 경보에서 새 사건을 만들거나 기존 사건에 연결하는 흐름을 제공합니다. 관련 관찰값·첨부·내용이 전송될 수 있으므로 옮겨진 범위와 공유 설정을 확인합니다. 상세 화면은 [공식 경보 전환 절차](https://docs.strangebee.com/thehive/user-guides/analyst-corner/alerts/create-a-case-from-an-alert/)를 따릅니다.

SIEM 경보 ID·규칙 버전·근거 레코드·검색 기간을 사건에 붙입니다. 검색 링크만 남기면 원본 보존 만료나 권한 변경 뒤 확인하지 못할 수 있습니다. 필요한 원문을 별도로 보존하고 그 위치·해시·수집 조건을 기록합니다.

## 3단계 — 관찰값과 증거를 구분하기

| 종류 | 가상 예시 | 해석 제한 |
| --- | --- | --- |
| Observable | LAB-FS01, lab-operator, 작업 이름 | 조사 대상 값이며 자동 악성 IOC가 아님 |
| 증거 레코드 | E004·E005·E007 | 무엇을 기록했는지 원문과 연결 |
| 분석 가설 | 작업이 해당 로그온과 관련됨 | 연결 조건·반증을 명시 |
| 필요한 자료 | Task Scheduler Operational | 아직 수집하지 않은 자료 |
| 조치 기록 | 추가 수집 요청 | 요청·실행·결과를 구분 |

IP·도메인·해시는 출처와 관찰 기간을 붙입니다. 예제 주소는 문서용이고 악성으로 판정하지 않습니다. 비밀번호·토큰·사용자 개인정보를 제목·태그에 넣지 않습니다. 파일 첨부가 필요한 경우 사건 접근 권한과 공유 범위를 먼저 확인합니다.

## 4단계 — 작업을 검증 가능한 단위로 나누기

‘호스트 조사’ 대신 ‘LAB-FS01의 해당 기간 Security 원문 보존’처럼 대상·입력·완료 결과를 지정합니다. 아래는 실제 조치를 수행한 기록이 아니라 학습 계획입니다.

| 작업 | 담당 역할 | 완료 증거 |
| --- | --- | --- |
| 원문·시간·장비 확인 | 분류 담당 | 원문 ID와 기간 표 |
| 작업 XML 이전·이후 비교 | 조사 담당 | 명령·인자·권한·트리거 차이 |
| 실제 실행 맥락 확인 | 호스트 수집 담당 | 부모·세션·실행 기록 또는 자료 부재 |
| 통신과 프로세스 연결 | 네트워크·호스트 담당 | 연결 식별자와 제한 |
| 승인·업무 영향 확인 | 서비스 담당 | 요청 기록·일치 여부 |
| 최종 판단·인계 | 조사 책임자 | 근거·미확인·후속 과제 |

작업이 실패하면 상태·원인·재시도 조건을 남깁니다. 완료 체크가 필요한 근거 수집 성공을 대신하지 않습니다.

## 5단계 — 타임라인과 조치 결과 보존하기

원본 발생 시각·시간대, 수집 시각, SIEM 도착과 분석·조치 시각을 분리합니다. 대상의 시계 오차도 적습니다. [증거 보존](evidence-timeline.html)과 [수집 지연](telemetry-health.html)을 함께 활용합니다.

조치에는 요청자·실행자·대상·방법·버전·시각·실제 결과·업무 영향을 기록합니다. 계정 제한 뒤 일부 서비스의 접근이 남아 있는지 검증합니다. ‘격리 API 성공’과 네트워크 확산 차단 확인은 서로 다른 근거입니다.

## 6단계 — 외부 분석과 공유를 통제하기

파일·URL·도메인을 외부 평판 서비스로 전송하면 내부 자료가 외부로 나갈 수 있습니다. 도구 통합의 요청·보관 정책과 사건의 공유 조건을 확인합니다. 먼저 내부 자료·기존 해시 정보로 확인 가능한지 검토합니다.

TLP는 정보 제공자의 공유 조건이며 사건의 심각도나 악성 신뢰도와 별개입니다. [TLP와 정보 카드](threat-intelligence-operations.html)를 사용합니다. AI 요약에는 원문 근거 ID를 요구하고 사건 기록·로그의 지시문을 운영 지시로 실행하지 않도록 [자동화 경계](soar-ai-operations.html)를 적용합니다.

## 7단계 — 종결과 인계의 근거 남기기

```text
사건 ID / 범위 / 현재 판단:
사실: 근거 ID와 확인 방법
가설: 지지 근거·반증·신뢰 한계
영향: 확인된 범위·미확인 범위
조치: 수행 시각·결과·업무 영향
수집 한계: 부재·기간·손실
남은 작업: 담당·기한·완료 증거
종결 또는 인계 이유:
```

정상으로 종결할 때도 승인과 실제 행동의 일치 근거를 남깁니다. 자료 부족으로 종료하면 ‘침해 없음’ 대신 확인할 수 없었던 범위와 잔여 위험을 적습니다. 신규 탐지·수집 작업은 사건에 연결해 완료 여부를 추적합니다.

**완료 기준:** 다른 분석가가 사실·가설·조치·남은 업무를 재확인합니다. [사건 기록 템플릿](downloads/blue-team-case-template.md)과 [통합 실습](blue-team-capstone.html)을 사용하세요.
