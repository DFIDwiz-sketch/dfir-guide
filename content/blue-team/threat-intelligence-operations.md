## 목표와 준비물

위협 인텔리전스는 보고서나 IOC 목록을 모으는 것에서 끝나지 않습니다. 우리 환경에 관련 있는 질문에 답하고 실제 조사·탐지·통제의 근거를 제공해야 합니다. MISP는 정보를 구조화·연결·공유하는 데 사용할 수 있고, 설치 없이 정보 카드로 같은 판단을 연습할 수 있습니다.

준비물은 공식 보고서 한 건, 자산·신원 목록과 [정보 카드 템플릿](downloads/blue-team-intelligence-template.md)입니다. 기존 [APT 보고서 분석](apt-analysis.html)에서 출처와 귀속의 한계를 먼저 확인합니다.

## 1단계 — 필요한 정보의 질문 정하기

‘북한 위협을 알아본다’보다 ‘우리 SaaS에서 비정상 인증 흐름 이후 장치 등록과 메일 규칙 생성이 있었는가’처럼 행동·대상·결정을 적습니다. 사용하지 않는 제품의 IOC보다 현재 사용 계정·서비스의 관측 공백을 먼저 다룹니다.

예시 질문: 외부 보고서의 device-code 인증 악용이 우리 환경에서도 가능한가? 필요한 답은 앱·인증 흐름·정책·로그·담당·후속 조사입니다. 보고서의 공격자 명칭 자체가 방어 조치의 대상은 아닙니다.

## 2단계 — 출처와 기간·신뢰를 구분하기

```text
정보 ID / 출처 기관 / 원문 URL:
발표·수정일 / 사건 관찰 기간 / 확인일:
직접 관찰된 행동 / 제공자 추정:
우리 환경의 관련 자산·조건:
분석 신뢰도와 이유 / 미확인 사항:
공유 범위 / 후속 검색 / 담당:
```

원문 URL과 확인일을 남기고 재배포 글보다 최초 분석을 우선합니다. 독립 관찰과 같은 보고서의 재인용을 구분합니다. 오래된 사건의 발표일을 공격 발생일로 바꾸지 않습니다. 지리 정보·도구 일치만으로 행위자나 사용자를 특정하지 않습니다.

## 3단계 — TLP 2.0 공유 조건 적용하기

| 등급 | 공유 범위 요약 |
| --- | --- |
| TLP:RED | 지정된 수신자만, 추가 공유하지 않음 |
| TLP:AMBER+STRICT | 수신 조직 내부의 필요한 사람으로 제한 |
| TLP:AMBER | 수신 조직과 고객에게 보호 목적의 need-to-know 공유 |
| TLP:GREEN | 관련 커뮤니티 안에서 공유, 공개 채널 금지 |
| TLP:CLEAR | 공개 공유 가능, 저작권 등 일반 조건은 여전히 적용 |

이 표는 [FIRST 공식 정의](https://www.first.org/tlp/)를 요약한 것입니다. TLP 2.0은 TLP:WHITE를 TLP:CLEAR로 변경했고, 조직 내부만 허용하는 TLP:AMBER+STRICT를 명확히 했습니다. 출처가 정한 범위를 임의로 넓히지 않습니다. 등급이 없으면 공개 가능한 것으로 추측하지 말고 정보 제공자의 조건을 확인합니다.

TLP는 악성 신뢰도·심각도·국가 보안 분류가 아닙니다. 도구에 태그를 붙였다고 전송·공유 권한이 자동으로 통제된다고 보지 않습니다. 공유 설정과 외부 API 전송을 따로 시험합니다.

## 4단계 — IOC를 맥락과 수명으로 관리하기

| 항목 | 기록할 이유 |
| --- | --- |
| 값·유형·관계 | IP·도메인·해시·URL과 어떤 행위에 연결됐는지 |
| first/last seen | 관찰된 유효 기간과 출처 |
| 신뢰·근거 | 알려진 악성, 의심, 단순 관찰값을 구분 |
| 공유 기반시설 여부 | CDN·프록시·호스팅 전체를 악성으로 처리하지 않기 |
| 용도·만료·담당 | 조사용·탐지용·차단용과 재검토 조건 |
| 내부 sighting | 실제 우리 자료에서 관찰한 시각·자산·원문 |

IOC 일치가 악성 실행·데이터 유출을 자동 증명하지 않습니다. 해시 불일치도 다른 버전·패킹·파일 부재의 가능성이 있습니다. 알려진 정상 값과 warninglist 일치를 추가 검토 대상으로 쓰고, 정상 목록이라는 이유로 무조건 경보를 제거하지 않습니다.

만료 날짜와 원인을 명확히 합니다. MISP의 기본 decaying 점수는 속성의 `to_ids`를 자동 해제하는 기능과 같지 않습니다. [공식 MISP playbooks](https://github.com/MISP/misp-playbooks)의 설명을 확인하고, 실제 해제·태그·동기화·탐지 반영을 별도로 검증합니다.

## 5단계 — MISP 구조와 사건 기록 연결하기

사용 버전에서 Event는 관련 정보를 묶고 Attribute·Object는 값과 관계를 구조화하는 데 활용합니다. taxonomy·galaxy·sighting·warninglist 등은 의미와 업데이트 경로를 확인합니다. `to_ids`는 IDS용 사용 의도를 나타내는 플래그이지 악성 확정 판정이 아닙니다. export 설정과 소비 도구의 실제 사용 방식도 확인합니다.

TheHive 사건과 MISP 정보는 역할이 다릅니다. 외부 보고서의 정보와 내부 조사 결과를 출처별로 보존하고 필요한 범위만 연결합니다. 공개 보고서 전체를 붙여 넣거나 내부 사건을 기본 공유 설정으로 외부에 동기화하지 않습니다.

**실습:** 예제 관찰값 `training.example.test`를 정보 카드에 적고, 학습용 정상 도메인임을 표시합니다. 탐지·차단용으로 표시하지 않고 E009의 관찰과 연결합니다. 실제 악성 IOC를 만든 실습이 아닙니다.

## 6단계 — 행동 가설을 탐지와 헌팅으로 연결하기

IOC 검색과 행동 검색을 따로 만듭니다. ‘보고서의 주소가 있나’와 ‘새 장치 등록 뒤 데이터 접근이 있었나’는 다른 질문입니다. 데이터가 없으면 [관측 지도](defensible-visibility.html)를 갱신하고 확인 불가로 기록합니다.

ATT&CK 기술뿐 아니라 [Detection Strategies](https://attack.mitre.org/detectionstrategies/)와 실제 필드를 확인합니다. 기관별 그룹 이름은 [Microsoft 현재 분류](https://learn.microsoft.com/en-us/defender-xdr/microsoft-threat-actor-naming) 등 원문을 대조하고 매핑 시점을 적습니다. 다른 기관의 비슷한 명칭을 완전히 같은 범위라고 자동 병합하지 않습니다.

## 7단계 — 정보의 운영 효과를 확인하기

정보가 실제 조사 후보·통제 변경·수집 개선으로 이어졌는지 기록합니다. 가져온 IOC 개수보다 우리 환경과 관련 있는 정보, 기한 내 검토, 만료된 차단, 조사 근거 제공 여부를 평가합니다. 분류가 끝난 경보만으로 정확도를 계산하고 미완료·자료 부족은 별도로 보입니다.

**완료 기준:** 원문·기간·공유 조건·IOC 사용 목적·만료·후속 행동이 포함된 정보 카드를 완성합니다. 다음은 [헌팅 절차](threat-hunting-workflow.html)입니다.
