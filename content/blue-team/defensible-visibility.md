## 목표와 준비물

방어 가능한 환경은 자산과 업무를 알고, 필요한 행위를 관측하며, 변경과 대응의 담당을 연결할 수 있는 환경입니다. 네트워크 그림 외에 신원·관리 경로와 로그 전달 경로도 필요합니다. 준비물은 키트 연결도, 자산 목록, source별 기대 이벤트와 원본 보존 기간입니다.

## 1단계 — 세 지도를 따로 만들기

| 지도 | 적을 항목 | 확인할 질문 |
| --- | --- | --- |
| 업무·자산 | 장비·서비스·중요 데이터·소유자 | 중단되면 어떤 업무가 영향을 받는가 |
| 연결·신원 | 통신 경로·인증 대상·관리 계정·앱 권한 | 누가 어느 서비스에 접근할 수 있는가 |
| 관측·자료 | 센서·로그 원본·collector·SIEM·보존 | 그 행동을 어떤 자료에서 확인하는가 |

IP 주소만으로 자산을 고정하지 않습니다. DHCP·NAT·VPN·컨테이너와 시간에 따른 변경을 고려하고 장비 ID·계정 ID·클라우드 리소스 ID를 붙입니다. Core와 Sensor를 분석 대상과 혼동하지 않도록 역할을 표시합니다.

## 2단계 — 사용자 키트의 수집 경계 표시하기

| 구성 | 역할 | 자료와 확인할 제한 |
| --- | --- | --- |
| Sensor + 대상망 측 TAP | 관찰된 트래픽 처리 | Zeek·Suricata·Arkime가 같은 관측 구간을 보는지 확인 |
| Core + 분석 측 스위치 | 검색·분석·수집 결과 보관 | Core에 연결됐다는 이유만으로 모든 통신이 TAP을 지나지는 않음 |
| 양쪽 인라인 방화벽 | 허용 경로와 접속 경계 | 방화벽 기록·NAT·시간과 실제 관측 구간 비교 |
| Velociraptor Hunt | 필요 시 호스트 증거 수집 | 과거 로그 보존·클라이언트 상태·artifact 조건에 의존 |
| 선택적 Client Monitoring | 특정 호스트 이벤트 지속 수집 | 별도 설정·전달·경보 검증이 필요 |

수동 TAP은 패킷을 관측하는 장치이며 격리나 차단을 수행하지 않습니다. TAP 위치 밖의 동일 VLAN 내부 통신, 다른 vSwitch, 클라우드 간 통신은 보이지 않을 수 있습니다. 실제 연결을 정상 시험으로 확인합니다.

## 3단계 — 행위별 증거 요구사항 정하기

먼저 조사 질문을 정하고 원본을 고릅니다. ‘예약 작업을 만들었는가’와 ‘그 작업이 실행됐는가’는 다른 질문입니다.

| 질문 | 필요한 자료 | 함께 점검할 조건 |
| --- | --- | --- |
| 호스트가 어디에 연결했는가 | Zeek conn·PCAP·방화벽·호스트 연결 | 센서 경로·드롭·암호화 |
| 어떤 사용자·프로세스가 만들었는가 | Security·Sysmon·EDR 등 | 감사 정책·필드·보존 |
| 파일·작업이 현재 존재하는가 | Hunt·관리 조회 | 현재 상태와 과거 실행 분리 |
| SaaS 계정이 무엇을 했는가 | 로그인·앱 동의·서비스 감사 | 테넌트·라이선스·API·보존 |
| 데이터가 읽히거나 전송됐는가 | 데이터 접근·내보내기·DLP·통신 | 관리 API 로그와 데이터 로그 차이 |

상시 호스트 로그가 없는 환경에서는 단명 프로세스가 Hunt 이전에 사라질 수 있습니다. 현재 프로세스 목록만으로 과거 행위를 부정하지 않습니다. 실시간 호스트 탐지가 필요하면 일부 중요 로그를 지속 수집하는 확장안을 별도 검증합니다.

## 4단계 — 정상 행동 하나를 원본까지 추적하기

허용된 시험 호스트에서 정상 DNS 조회·웹 접속 또는 무해한 예약 작업을 수행합니다. UTC 시각, 장비, 계정, 목적을 적습니다. 센서 원본 → 처리 로그 → SIEM 원문 → 검색·경보를 차례로 비교합니다.

**결과가 없을 때:** 원본 생성 여부 → 경로·센서 → 패킷 손실·필터 → 전달 → 인덱스·시간 → 필드 매핑을 확인합니다. 각 단계에서 자료 ID와 결과를 남깁니다. Hunt가 성공했다는 표시와 필요한 이벤트가 수집됐다는 사실을 구분합니다.

## 5단계 — 암호화와 임시 자산의 공백 채우기

TLS·QUIC·암호화 DNS 환경에서는 payload나 특정 이름 정보가 가려질 수 있습니다. 복호화 가능 여부를 먼저 확인하고, 없으면 DNS·프록시·서비스 감사·호스트 프로세스와 연결합니다. [암호화 가시성](encrypted-network-visibility.html)을 참고합니다.

클라우드와 컨테이너는 생성·삭제가 빠르므로 리소스 ID·이미지 digest·배포 기록·관리 API와 실행 증거를 연결합니다. 업무 단말의 TAP만으로 SaaS의 서버 측 행위를 모두 볼 수 없습니다. 관리 로그가 있다고 파일 접근 감사도 켜졌다고 가정하지 않습니다.

## 6단계 — 우선순위·비용·보존을 함께 설계하기

보존해야 할 자료와 즉시 검색해야 할 자료를 구분합니다. 모든 로그를 고가 SIEM에 넣는 대신, 위험과 조사 목적에 맞춰 중요 source를 우선 수집하고 다른 자료는 적절한 중앙 보존·복원 경로를 정할 수 있습니다. 이는 2025년 ASD 지침의 방향과 연결됩니다.

보존 기간은 탐지·조사 지연, 업무·규정 조건, 저장 용량과 복원 시간을 고려해 정합니다. 한 기간을 모든 조직에 공통으로 권하지 않습니다. PCAP에는 실제 payload가 포함될 수 있어 접근·반출·보존 통제를 로그와 함께 설계합니다.

## 7단계 — 관측 공백에 담당과 검증일 붙이기

```text
행위 / 대상 / 중요한 이유:
원본 / 수집 방식 / 검색 위치:
마지막 정상 시험 / 근거 ID:
누락 구간 / 보존 만료 / 시간 제한:
보완 방법 / 담당 / 다음 검증일:
```

**완료 기준:** 현재 탐지할 수 있는 것, 과거 자료로만 조사할 수 있는 것, 확인 불가한 것을 나눕니다. 다음은 [경보 분류](alert-triage.html)와 [수집 상태·지연](telemetry-health.html)입니다.
