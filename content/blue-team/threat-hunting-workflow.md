## 목표와 준비물

위협 헌팅은 경보가 없어도 위협 가설을 자료로 검증하는 조사입니다. 많은 로그에서 이상한 문자열을 찾는 것만으로는 충분하지 않습니다. 대상·기간·필요 자료·정상 기준·반증·판단 한계를 먼저 정합니다.

준비물은 [관측 지도](defensible-visibility.html), 출처가 확인된 정보 카드, 자산·계정 맥락입니다. 실습에는 가상 자료를 사용하고 악성 행동을 재현하지 않아도 됩니다.

## 1단계 — 검증할 질문을 한 문장으로 쓰기

예: ‘LAB-FS01에서 네트워크 로그온 뒤 예약 작업 생성·변경이 관찰되며, 실행과 승인 맥락이 있는가?’ 창의적인 공격자 이야기를 만드는 대신 확인 가능한 질문을 적습니다.

핵심 가정은 대상 로그가 남아 있고 해당 기간·장비를 관측한다는 것입니다. 실제 운영에서는 도메인 관리자·배포·백업 같은 고권한 경로, 경계 장비와 SaaS 토큰을 중요한 대상으로 검토합니다. 유행하는 사례가 우리 환경과 관련 있는지 먼저 확인합니다.

## 2단계 — 필요한 자료와 반증 조건 정하기

| 가설 부분 | 필요한 근거 | 반증·대안·제한 |
| --- | --- | --- |
| 네트워크 로그온과 작업 관련 | 같은 장비·세션·기간의 기록 | 다른 사용자·다른 장비·로그 초기화 |
| 작업 실행 | Task Scheduler·부모·실행 맥락 | 직접 연결 부재·다른 실행 원인 |
| 미승인 관리 | 작업 승인·정상 관리 기준 | 승인된 실행과 일치하는지 |
| 통신 관련 | 프로세스와 연결의 식별 정보 | 공유 서비스·다른 프로세스 |
| 데이터 유출 | 대상 데이터·읽기·전송·내용 근거 | TLS 연결과 바이트 수만 있음 |

로그가 없으면 ‘가설 반증’이 아니라 관측 불가일 수 있습니다. 정상 승인도 다른 악성 행위의 부재를 증명하지 않습니다. 어떤 질문에 답했는지 좁혀서 기록합니다.

## 3단계 — 정상 기준을 역할·시간으로 만들기

관리 서버, 사용자 단말, DC·파일 서버는 정상 활동이 다릅니다. 작업 실행 계정·원격 관리 출발점·시간대·설치 경로·부모 프로세스·목적지를 역할에 맞춰 봅니다. 한 번 본 행동을 바로 정상 기준으로 만들지 않습니다.

LOTL은 PowerShell·systemctl·curl 같은 정상 도구를 악용합니다. 서명이나 이름보다 실제 목적과 실행 맥락을 확인합니다. [공동 LOTL 지침](https://www.cyber.gov.au/advisory/identifying-and-mitigating-living-off-the-land-techniques)은 정상 기준과 상세 로그의 중요성을 강조합니다. [Linux 지속성](linux-persistence.html)·[예약 작업](scheduled-tasks.html)과 연결합니다.

## 4단계 — 작은 대상에서 후보를 찾기

처음에는 대상 장비 하나와 좁은 기간에서 원문을 확인합니다. 이후 계정·작업 이름·인증 출발점·프로세스·목적지로 범위를 넓힙니다. source가 하나의 JSON sourcetype에 섞였다면 실제 종류·장비·artifact를 확인합니다.

가상 자료에서는 E004의 성공 로그온, E005의 생성, E007의 변경, E012의 삭제를 봅니다. E006의 프로세스 기록은 실행 맥락을 더 조사할 단서입니다. 하나의 IP나 가까운 시각만으로 E008의 TLS 연결을 해당 PowerShell에 연결하지 않습니다.

**결과가 0개일 때:** 기간·대상·인덱스·필드·원본·수집을 [Splunk 검색](splunk-basics.html)과 [수집 점검](telemetry-health.html)에 따라 확인합니다. 가설이 틀렸다는 결론은 자료 조건을 확인한 뒤 내립니다.

## 5단계 — 호스트·네트워크·신원의 연결 확인하기

| 수집 방법 | 확인할 결과 | 제한 |
| --- | --- | --- |
| Velociraptor Hunt | EVTX·작업 정의·파일 등 필요한 자료 | 현재 상태·대상·권한·보존에 의존 |
| Zeek·Arkime·Suricata | 흐름·세션·경보·관측 payload | 센서 범위·암호화·손실 |
| 인증 로그 | 검증·서비스 로그온·계정 사용 | 성공만으로 실제 데이터 접근 확정 못함 |
| 클라우드 감사 | 앱·세션·장치·메일·데이터 작업 | 테넌트·라이선스·API·보존 |

현재 키트의 필요 시 Hunt는 과거 단명 프로세스를 항상 복원하지 못합니다. 중요한 질문은 원본 EVTX·EDR·지속 이벤트 수집 여부까지 확인합니다. 다른 자료를 연결할 키·시각·범위를 남깁니다.

## 6단계 — 가설별 결과를 기록하기

‘관찰 사실 확인’, ‘충분한 자료에서 불일치’, ‘자료 부족으로 판단 보류’, ‘추가 조사 후보’를 구분합니다. C2·유출·공격자 귀속은 각각 필요한 근거가 다릅니다. 후보가 나왔다면 [경보 분류](alert-triage.html)와 [사건 관리](case-management.html)로 넘깁니다.

최근 device-code 피싱을 헌팅한다면 인증 흐름 이후 장치 등록·앱 권한·메일 규칙·데이터 접근을 연결합니다. 정상 계정과 관리 도구만 보인다는 이유로 부재 판정을 내리지 않습니다. [클라우드 대응](cloud-identity-response.html)의 조건을 확인합니다.

## 7단계 — 개선 과제와 다시 볼 조건 정하기

헌팅에서 찾은 필드 누락·미수집·정상 관리 맥락·의심 후보를 각각 작업으로 바꿉니다. 반복 관찰 가능한 행동은 [탐지 명세](siem-use-case-lifecycle.html)로 만들고, 조치가 필요한 영향은 [초기 대응](incident-triage.html)으로 연결합니다.

**완료 기준:** 가설·대상·기간·자료·정상 기준·반증·결과·미확인·후속 작업을 다른 분석가가 재현할 수 있게 작성합니다. ‘악성 0건’이 유일한 결과물이 되어서는 안 됩니다.
