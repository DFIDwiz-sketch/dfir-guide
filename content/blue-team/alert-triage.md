## 목표와 준비물

경보는 확인할 조건이 충족됐다는 신호입니다. 악성 행위와 피해가 자동으로 확정되는 것은 아닙니다. **이벤트는 관찰 기록, 이상 징후는 기대와의 차이, 경보는 규칙이나 도구의 알림, 사건은 대응이 필요한 보안 상황**으로 구분해 생각합니다. 실제 사건 정의는 조직의 정책을 따릅니다.

준비물은 경보 원문·규칙 버전·자산 정보·대상 기간입니다. 연습에는 [가상 로그](first-investigation.html)를 사용합니다. 가상 주소와 계정을 운영 차단 목록에 넣지 않습니다.

## 1단계 — 경보 제목보다 원문 확인하기

경보 ID, 규칙 목적, 근거 이벤트 ID, 발생 시각과 SIEM 도착 시각, 실제 대상 장비와 collector를 확인합니다. ‘의심 PowerShell’이라는 제목만으로 악성 명령을 실행했다고 쓰지 않습니다.

E005는 예약 작업 생성 기록, E007은 변경 기록입니다. 작업 XML에 PowerShell이 있다는 사실은 확인할 수 있지만, 그 정의만으로 실행·침해·지속성 성공을 모두 증명하지는 못합니다. [탐지 실습](blue-detection.html)의 목적도 후보 검색입니다.

## 2단계 — 자료 품질과 긴급성을 병렬 확인하기

| 분류 축 | 질문 | 남길 내용 |
| --- | --- | --- |
| 근거 품질 | 원문·핵심 필드·시간이 재확인 가능한가 | 파서 문제·중복·누락 |
| 자산·권한 | 중요 서비스·관리자·배포·백업인가 | 실제 역할·업무 영향 |
| 현재 행동 | 활동·확산·변경이 계속되는가 | 최근 원문과 다른 자산의 징후 |
| 데이터 영향 | 접근·변경·외부 전송 증거가 있는가 | 데이터 종류와 확인 제한 |

확인된 확산이나 중대한 피해가 있으면 분석 완료를 기다리지 않고 [초기 대응](incident-triage.html)에 따라 보존·억제를 병행합니다. 자료 부족은 낮은 위험의 증거가 아닙니다. 긴급성, 근거 신뢰도와 미확인 범위를 별도 표시합니다.

## 3단계 — 같은 자산의 앞뒤 맥락 찾기

아래 `lab_logs`를 실제 학습 인덱스로 바꾸고 Time Picker를 **2026-10-07의 가상 자료 기간**에 맞춥니다. JSON 필드를 확인한 후 사용합니다. 이는 가상 자료용 예제이며 실제 Splunk 실행 검증을 완료한 운영 규칙은 아닙니다.

```spl
index=lab_logs
| spath
| where ComputerName="LAB-FS01"
| table timestamp record_id EventCode TargetUserName SubjectUserName
    TargetLogonId SubjectLogonId TaskName CommandLine
| sort 0 timestamp
```

한 번 수집한 원본 12개에서 기대 기록은 E004·E005·E006·E007·E011·E012의 **6개**입니다. `timestamp`는 이 실습의 원본 필드입니다. 운영 데이터에서는 `_time`과 원본 시간 해석을 비교합니다.

같은 LAB-FS01의 E004 `TargetLogonId`와 E005·E006·E007의 `SubjectLogonId`는 세션 맥락을 잇는 단서입니다. E011은 다른 계정의 실패 기록이므로 이 흐름에 자동으로 합치지 않습니다. 장비·세션·시간을 함께 확인합니다.

## 4단계 — 정상 설명과 악성 가설을 같이 쓰기

| 관찰 | 가능한 정상 설명 | 확인할 추가 자료 |
| --- | --- | --- |
| PowerShell 작업 생성·변경 | 승인된 관리·교육 | 작업 요청·이전 XML·실제 실행 |
| 성공한 NTLM 네트워크 로그온 | 정상 파일 서비스 사용 | 원래 클라이언트·대상 접근·권한 행사 |
| 외부 TLS 연결 | 업데이트·일반 업무 | 프로세스 연결·프록시·서비스 기록 |
| 로그인 실패 한 건 | 잘못 입력·저장된 암호 | 반복 패턴·다른 계정·정상 작업 |

승인 기록은 중요한 맥락이지만 공격자가 승인된 관리 도구나 계정을 악용할 가능성을 없애지는 않습니다. 정상 설명도 현재 관찰과 일치하는지 확인합니다. 디지털 서명·MFA 성공·암호화라는 이유만으로 종료하지 않습니다.

## 5단계 — 후보 상태를 분명하게 결정하기

| 상태 예시 | 의미 | 다음 행동 |
| --- | --- | --- |
| 의심 지속·조사 필요 | 후보 근거가 있고 원인 미확인 | 담당 배정·추가 수집 |
| 확인된 정상 행위 | 범위와 승인·실행 맥락이 일치 | 근거 기록·예외 검토 |
| 규칙·파서 오류 | 의도와 다른 입력이 일치 | 탐지·플랫폼 작업 연결 |
| 자료 부족·확인 불가 | 핵심 로그 부재·보존 만료 | 제한·추가 수집·잔여 위험 기록 |
| 확인된 보안 사건 | 조직의 사건 기준과 근거 충족 | 사고 대응 체계로 전환 |

규칙이 ‘예약 작업 생성’을 찾았다면 정상 생성도 조건에는 맞습니다. 탐지 일치와 실제 악성 여부를 나눠야 오탐 지표가 왜곡되지 않습니다. 상태 명칭은 조직에 맞춰 조정하되, 자료 부족을 정상과 합치지 않습니다.

## 6단계 — 최근 신원 위협을 조사 범위에 넣기

device-code 피싱·세션 탈취에서는 사용자 단말에 새 악성 파일이 없어도 클라우드 계정이 악용될 수 있습니다. 사용한 인증 흐름·앱·리소스·장치 등록·메일 규칙·데이터 접근을 [클라우드 조사](cloud-identity-response.html)에 연결합니다. MFA 성공 기록만으로 정당한 후속 사용을 보장하지 않습니다.

LOTL과 RMM은 정상 도구 이름을 그대로 사용할 수 있습니다. 실행 계정·부모·인자·목적지·설치 승인·후속 행동을 보고 [ClickFix·RMM 조사](clickfix-rmm-investigation.html)로 확장합니다.

## 7단계 — 다음 담당이 재현할 수 있게 인계하기

‘의심됨’ 대신 사실 2개, 정상 설명 1개, 미확인 2개, 다음 수집 1개를 적습니다. 예: E005·E007의 작업 정의를 확인했으나 E006이 해당 작업의 실행이라는 직접 연결은 미확인. Task Scheduler Operational·부모 프로세스 또는 EDR 실행 맥락이 필요합니다.

**완료 기준:** 경보 상태와 긴급성의 근거를 설명하고 원문 검색·남은 조사·담당을 인계합니다. 다음은 [사건 관리](case-management.html)입니다.
