## 출처와 사건 범위를 먼저 확인하기

보고서의 발표일, 대상 사건 기간, 작성 기관과 근거를 남깁니다. 같은 그룹 이름이라도 기관마다 분류 범위가 다를 수 있습니다. 특정 도구·IP·기술의 관찰만으로 공격자 귀속을 단정하지 않습니다.

## 보고서를 정리하는 형식

| 항목 | 기록할 내용 |
| --- | --- |
| 출처 | 원문 URL, 작성 기관과 확인 날짜 |
| 사건 | 대상과 시간 범위, 공개된 사실 |
| 행동 | 관찰된 행위와 조건 |
| ATT&CK | 기술 ID와 매핑의 이유 |
| 증거 | 호스트·네트워크·계정에서 확인할 자료 |
| 신뢰도 | 확인, 보고서 추정, 분석 가설의 구분 |
| 검증 | 랩에서 시험할 데이터와 성공 기준 |

ATT&CK의 그룹 페이지는 보고된 여러 사건의 기술을 모을 수 있습니다. 목록을 한 사건의 공격 순서로 그대로 읽지 않습니다.

## IOC와 행동을 함께 보기

파일 해시·주소·도메인은 구체적인 자료를 찾는 단서입니다. 값이 바뀌어도 반복되는 프로세스 관계, 인증 흐름과 지속성 변경 등의 행동 조건을 함께 조사합니다. 보고서의 IOC만 검색하고 결과가 없다고 가설을 모두 기각하지 않습니다.

## 실습으로 바꾸기

공개된 행동 하나를 고르고 통제된 랩에서 관찰할 데이터와 예상 결과를 정의합니다. 실제 피해 환경·운영 세부사항을 복사하기보다 기술의 원리와 방어 관찰을 시험합니다. [퍼플팀 검증 루프](purple-validation.html)와 [주간 ATT&CK 노트](weekly-technique.html)를 함께 활용하세요.

## 최근 보고서 한 건을 실제 헌팅으로 바꾸기

[2026 보안 우선순위](security-priorities-2026.html)에서 원문 한 건을 선택하고 다음 순서로 기록합니다.

1. 발표일과 실제 관찰 기간, 수정 이력을 적습니다.
2. 보고서가 직접 관찰한 행동과 작성 기관의 추정을 분리합니다.
3. 우리 조직에 같은 제품·권한·노출 조건이 있는지 확인합니다.
4. 필요한 이벤트·필드·보존 기간이 실제 있는지 점검합니다.
5. 특정 IOC와 반복 가능한 행동 조건을 별도 검색으로 구성합니다.
6. 정상 사례·반증과 함께 후보를 조사하고 개선 사항을 기록합니다.

ATT&CK 기술 ID·플랫폼·정의는 원문에서 확인하고 열람 날짜를 남깁니다. 탐지 문서를 복사할 때도 데이터 요구사항·전제·버전을 기록합니다. ATT&CK에 매핑됐다는 사실은 해당 기법 전체를 탐지한다는 증거가 아닙니다.

| 조사 상태 | 보고서에 쓸 표현 |
| --- | --- |
| 필요한 원문과 관련 행위를 확인 | 어떤 자료의 어떤 필드로 확인했는지 명시 |
| 자료는 충분하나 조건과 불일치 | 검색 기간·대상·가설과 불일치 근거 명시 |
| 원본 수집이 없거나 보존 만료 | 확인 불가와 필요한 추가 자료 명시 |
| 일부 유사 행동만 존재 | 후보와 정상 설명·반증을 함께 기록 |

**완료 기준:** 공격자 이름을 반복하는 요약을 넘어, 재현 가능한 검색 범위와 근거 이벤트, 미확인 조건을 포함한 조사 메모를 작성합니다.
