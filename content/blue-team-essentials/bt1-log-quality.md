## 중앙화는 자료를 모으는 것에서 끝나지 않는다

기록이 한 위치에 있어도 같은 계정이 서로 다른 필드 이름으로 저장되거나 시각이 잘못 해석되면 연관 분석이 실패합니다. 수집 파이프라인에는 원본 전달, 파싱, 필드 정규화, 시각 해석, 저장, 검색 권한과 보관이 포함됩니다. 각 단계가 어느 자료를 잃거나 바꿀 수 있는지 확인해야 합니다.

예를 들어 호스트의 `username`, SaaS의 `principal`, 프록시의 인증 사용자 값을 하나의 검색 필드로 정규화할 수 있습니다. 하지만 표시 이름과 고유 계정 ID를 구별하지 않고 합치면 동명이인이나 계정 변경으로 오연결이 생깁니다. 공통 필드와 함께 원래 식별값·출처를 보존하는 이유입니다.

## 발생·수신·처리 시각을 구분하기

| 시각 | 의미 | 분석에 쓰는 방식 |
| --- | --- | --- |
| 발생 시각 | 출처가 기록한 행동 시각 | 타임라인과 시간 관계 |
| 수신 시각 | 수집 측이 받은 시각 | 전송·API 조회 지연 |
| 인덱싱 시각 | 검색 저장소에 반영된 시각 | 처리 큐·검색 가능 지연 |

공통 사례 D07의 발생 시각은 08:04, `received_at`은 08:12 UTC입니다. 발생 시각으로 정렬하면 로그인 이후의 설정 변경으로 보이고, 수신 시각으로 정렬하면 사용자 확인보다 늦게 들어온 자료처럼 보일 수 있습니다. 두 시각 중 하나가 잘못됐다고 단정하지 말고 지연이 있는지 확인합니다.

시각에는 UTC 또는 명확한 오프셋을 사용하고 원래 시각의 해석을 남깁니다. 브라우저가 현지 시간대로 표시하면 화면의 숫자가 달라질 수 있습니다. 출처의 시계 오차도 남을 수 있으므로 초 단위 순서를 강하게 주장할 때는 동기화 상태와 오차를 고려합니다.

## 네 가지 품질 문제를 다르게 처리하기

| 현상 | 가능한 원인 | 먼저 할 확인 |
| --- | --- | --- |
| 결과 0건 | 잘못된 시간·인덱스·필드·권한, 실제 부재 | 조건을 넓혀 원문 한 건부터 확인 |
| 필드가 비어 있음 | 출처 미기록, 파서 변경, 매핑 오류 | 원문에 값이 있는지 대조 |
| 같은 행동이 여러 번 보임 | 재전송, 복수 제품 경보, 실제 반복 | 출처 ID·요청·세션·관련 ID 확인 |
| 기록이 늦게 나타남 | API 주기, 제한, 큐 적체, 재시도 | 발생·수신·저장 시각과 수집 상태 |

중복 경보 두 건을 동일한 공격 행동 두 번으로 세지 않습니다. 반대로 같은 계정의 서로 다른 세션을 하나로 지우면 범위를 잃을 수 있습니다. 중복 제거 기준은 자료마다 다르므로 원본 식별자와 변환 기록을 유지합니다.

## 원문·정규화·보관의 관계

검색 편의를 위해 정규화하더라도 중요한 판단은 원문과 대조할 수 있어야 합니다. 원문 접근을 아무에게나 허용하라는 뜻은 아닙니다. 민감한 값이 포함될 수 있으므로 승인된 역할이 필요한 기간과 범위에 접근하도록 관리합니다. 접근·변경·보존 정책은 사건 대응 요구와 조직의 데이터 정책을 함께 고려합니다.

자주 검색하는 자료와 장기간 보관하는 자료의 저장 방식은 다를 수 있습니다. 차가운 저장소로 옮겨진 자료가 즉시 검색되지 않는다면 복원 시간과 담당을 기록합니다. 로그 보관과 PCAP 보관도 별개입니다. “SIEM에 있으니 원문도 남아 있다”라고 가정하지 않습니다.

## 수집 상태를 탐지의 일부로 관리하기

기대 출처의 마지막 정상 수신, 처리 오류, 필수 필드 채움 비율, 지연을 점검합니다. 이벤트가 드문 시스템은 건수가 0이라고 곧 수집 실패로 볼 수 없으므로 정상 활동 패턴이나 수집 작업 상태를 함께 봅니다. 임계값은 출처의 예상 주기와 업무 변화에 맞춰 정합니다.

학습 활동으로 D07의 지연을 계산하고 D16을 타임라인에 표시하세요. D16은 공격 행동이 아니라 증거 공백입니다. 결과 문장에는 “제공 자료 범위에서는 …를 확인했고, …는 자료가 없어 판단하지 못했다”를 사용합니다. 이는 탐지 실패와 자료 부재를 구별하는 연습입니다.
