## 직함보다 필요한 역할을 먼저 정하기

분류 담당은 경보의 관련성과 우선순위를 확인합니다. 조사 담당은 추가 자료를 연결해 범위와 영향을 검증합니다. 탐지 엔지니어는 데이터·규칙·예외·검증 자료를 관리합니다. 사건 대응 담당은 조치를 조율하고, 시스템 운영자는 실제 서비스 변경을 수행합니다. 위협 인텔리전스와 포렌식은 필요한 맥락과 상세 증거를 제공합니다.

작은 팀에서는 한 사람이 여러 역할을 맡아도 됩니다. 다만 **사건 책임자, 현재 작업 담당, 변경 승인자**는 구별해야 합니다. 사건 책임자가 모든 작업을 직접 한다는 뜻은 아닙니다. 작업이 중단됐을 때 다음 결정을 조율할 사람이 있다는 뜻입니다.

## Tier 구조와 협업 구조를 비교하기

| 운영 방법 | 유용한 상황 | 관리해야 할 문제 |
| --- | --- | --- |
| 단계별 Tier | 초기 확인을 표준화하고 복잡한 사건을 전문 담당에게 인계 | 인계 대기, 맥락 손실, 같은 질문 반복 |
| 역할 중심 협업 | 소규모 팀, 복합 사건, 전문가 공동 조사 | 주인 없는 작업, 중복 조사, 책임 경계 |

어느 구조든 완료 조건 없는 전달은 인계가 아닙니다. “확인 부탁” 대신 경보 ID, 검색 범위, 확인된 사실, 미확인 질문, 긴급도, 다음 작업을 남깁니다. 긴급 사건은 상세 양식을 모두 채울 때까지 인계를 지연하지 않되, 우선 전달한 내용과 이후 보완할 항목을 기록합니다.

## 한 경보가 처리되는 과정

| 단계 | 공통 사례의 입력 | 담당의 작업 | 단계 결과 |
| --- | --- | --- | --- |
| 수집 | D05 로그인, D07 메일 설정 감사 | 시각·필드·수집 지연 확인 | 분석 가능한 자료와 공백 |
| 탐지 | D05가 새 장치 조건과 일치 | D06 경보 생성 | 조건과 원문 연결 |
| 분류 | 계정 중요도, D08 정책 경보 | 두 경보의 관계와 우선순위 검토 | 하나의 조사 책임자 |
| 조사 | 세션 S002, D11·D12 확인 | 사용자·운영자 확인과 추가 세션 조회 | 근거·범위·미확인 영향 |
| 대응 | D13 요청 | 운영자 승인·실행, D14 확인 | 조치 대상과 결과 기록 |
| 개선 | D07의 늦은 수신, D16 공백 | 감사 지연과 탐지 범위 개선 | 담당·기한 있는 개선 작업 |

이 순서는 되돌아갈 수 있습니다. 조사 중 다른 계정이 발견되면 수집 범위를 늘리고 우선순위를 다시 정합니다. 대응 후 새 행동이 관측되면 조치 효과를 재평가합니다. 폐기 요청을 보내고 사건을 종결하는 직선 흐름으로 이해하면 안 됩니다.

## 인계 기록을 실제로 작성하기

~~~text
사건: LAB-BT1-20261008 / 현재 담당: 교육 분석가
관측: D05 새 장치 로그인 → D07 같은 세션의 전달 규칙 생성
확인: D11 사용자는 세션 부인, D12 운영자는 미승인 규칙 확인
분리: D09·D10 내부 PC 정상 활동은 세션 S002 관련 근거 없음
조치: D13 폐기 요청, D14 서비스 감사 성공
남은 질문: 실제 전달 메일, 다른 세션·토큰, 규칙 제거 확인
공백: 미관리 장치 호스트 자료 없음(D16)
다음 담당: 메일 운영자 / 다음 작업: 범위 조회와 조치 검증
~~~

인계 받은 사람은 원문 ID를 이용해 판단을 재검토할 수 있습니다. 최초 분석가가 조회했던 화면 캡처만 있고 시간 범위나 검색 조건이 없으면 같은 결과를 얻기 어렵습니다. 원문·검색·업무 확인의 출처를 함께 남기는 것이 중요합니다.

## 병목을 발견하는 학습 활동

각 단계의 시작·끝 시각을 가정해 워크북에 표시합니다. 분류는 빠르지만 조치 승인에 오래 걸렸다면 탐지 규칙을 더 많이 만드는 것으로는 지연이 줄지 않습니다. 승인 경로와 비상 담당을 개선해야 합니다. 반대로 자료 수신이 늦었다면 알림 이후 분석 시간을 줄여도 사건 발생부터 인지까지의 지연은 남습니다.

완료 기준은 한 사건에서 “누가 지금 무엇을 하고 있고, 무엇을 기다리며, 어떤 결과로 다음 단계에 갈지”를 설명할 수 있는 것입니다.
