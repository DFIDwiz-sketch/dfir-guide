## HTTP는 업무와 공격이 공유하는 통신 수단이다

HTTP(S)는 파일 전달, 로그인과 API, 원격 관리와 명령 제어, 자료 전송에 모두 사용될 수 있습니다. HTTPS가 있다는 사실은 전송 보호의 단서이며 콘텐츠 안전성의 보증은 아닙니다. 반대로 POST·Base64·반복 호출 자체도 악성 사용을 뜻하지 않습니다.

교재의 평판·화면 확인·샌드박스, 헤더·User-Agent, 인코딩, 파일 추출, 주기성, 웹 공격과 TLS 관측을 세 상세 글로 나누어 다룹니다. 특정 옛 exploit kit나 제품 버전보다 현재에도 적용되는 조사 방법에 집중합니다.

## 공격 단계와 필요한 증거

| 의심 상황 | 네트워크 후보 | 추가 확인 |
| --- | --- | --- |
| 피싱 링크 | 메일→URL·이동 경로 | 페이지·입력·계정·사용자 확인 |
| 파일 전달 | GET·응답·객체 해시 | 저장·실행·원인 프로세스 |
| 웹 취약점 시도 | 이례적 입력·IDS/WAF 후보 | 서버 처리·패치·후속 행동 |
| 명령 제어 후보 | 반복 GET/POST·상대·기간 | 정상 앱·단말 동작·프로그램 |
| 유출 후보 | 외부 업로드·규모·본문 맥락 | 실제 자료·승인·서버 결과 |

공통 자료 N05는 이동, N07은 무해한 교육용 문서 응답, N08은 경보 후보, N15는 POST 수락입니다. N16~N18은 승인된 모니터의 반복 호출입니다. 파일 전달·주기성·상태 코드만으로 침해 성공을 판정하지 않는 연습을 합니다.

## 분석 절차

먼저 시간·자산·URL·관측 위치·자료 품질을 보존합니다. 다음으로 요청과 응답을 연결하고 도메인 전체와 개별 경로, 다운로드 객체와 단말 실행을 구별합니다. 평판·샌드박스는 보완 자료로 사용하되 미탐을 정상 판정으로 바꾸지 않습니다. URL의 토큰·개인 정보와 파일의 내부 정보를 외부 제출하기 전 공유 범위를 검토합니다.

## 2022년부터 현재까지 달라진 가시성

TLS 1.3에서 서버 인증서 메시지는 일반적인 수동 캡처에서 암호화되어 있습니다. 서버 인증서 개인키만으로 모든 현대 TLS 세션을 복호화할 수 없습니다. 2026년 3월 RFC 9849로 표준화된 ECH는 실제 ClientHello의 이름 정보를 보호하므로 “SNI는 계속 보인다”는 전제도 상황별로 확인해야 합니다.

JA3·JA4 같은 지문은 클라이언트 특성을 좁히는 단서입니다. 여러 정상·악성 프로그램이 같은 지문을 공유할 수 있고 구현·버전·설정에 따라 바뀝니다. 지문 한 값으로 특정 악성코드나 사용자를 확정하지 않습니다.
