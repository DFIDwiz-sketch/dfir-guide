## URL의 이름과 경로를 각각 보존하기

분석 중 URL을 분해하더라도 원문을 남깁니다. 호스트는 DNS 이름이며 path와 query는 서버의 자원·처리 입력과 관련됩니다. path가 논리적 API일 수 있어 파일 확장자가 없다고 비정상은 아닙니다. fragment는 일반적으로 서버로 보내는 HTTP 요청 대상에 포함되지 않습니다.

Percent encoding은 URL의 문자를 표현하는 방식입니다. 디코딩 전후를 같이 기록하고 무조건 반복 디코딩하여 원래 구분자를 바꾸지 않습니다. query에는 업무·인증 관련 값이 들어갈 수 있어 URL을 외부에 공유하기 전 보존 목적과 민감 정보를 검토합니다.

## 요청의 구조를 읽기

~~~http
GET /invoices/2026 HTTP/1.1
Host: portal.study.example
User-Agent: TrainingBrowser/1.0
~~~

첫 줄은 메서드·요청 대상·버전, 이후는 헤더입니다. 헤더와 본문은 빈 줄로 나뉩니다. 이 자체 예의 GET에는 본문이 없습니다. 실제 HTTP 의미에서 GET 요청의 콘텐츠에는 일반적으로 정의된 목적이 없고 서버가 거절할 수 있으므로 “GET은 절대 바이트 본문을 가질 수 없다”와 같이 단정하지 않습니다.

POST는 어떤 처리를 요구하는지 자원의 계약에 따라 달라집니다. POST라는 메서드는 암호화 기능이 아닙니다. HTTPS 등 적절한 전송 보호가 없으면 본문이 보일 수 있으며 서버·프록시가 기록할 수도 있습니다.

## 메서드의 의미와 상태 코드

GET·HEAD는 조회 중심의 safe 메서드이지만 실제 서버의 부수 동작까지 없다고 보장하는 말은 아닙니다. PUT·DELETE 같은 idempotent 의미는 같은 요청을 반복했을 때 의도한 효과에 관한 것이며 모든 응답 코드가 항상 같다는 뜻은 아닙니다. OPTIONS는 지원 기능 조회에, CONNECT는 프록시를 통한 터널 설정 등에 사용할 수 있습니다. 승인된 프록시의 CONNECT를 악성 터널로 자동 분류하지 않습니다.

| 코드 | 일반적인 의미 | 후속 확인 |
| --- | --- | --- |
| 200 | 요청 성공 | 본문·앱 처리·요청 목적 |
| 202 | 처리 수락, 완료는 미보장 | 작업 상태·서비스 결과 |
| 302 | 다른 위치로 이동 지시 | Location·다음 실제 거래 |
| 304 | 조건부 요청의 미변경 | 기존 캐시·새 본문 없음 |
| 401 | 필요한 유효 인증 정보 부족 | 인증 challenge·후속 인증 |
| 403 | 요청을 이해했으나 거절 | 권한·정책·서버 처리 |
| 404 | 자원을 찾지 못했거나 공개하지 않음 | 경로·앱 라우팅·의도 |
| 500 / 503 | 내부 오류 / 서비스 불가 | 서버 상태·장애·후속 성공 |

상태 코드는 각각의 응답에 적용됩니다. 반복 404가 경로 탐색 후보일 수 있지만 오타·깨진 링크도 원인입니다. 500이 웹 공격의 성공을 증명하지도 않습니다. 정상 기준과 서버 감사로 원인을 확인합니다.

## 요청 헤더의 의미와 신뢰

| 헤더 | 얻는 맥락 | 한계 |
| --- | --- | --- |
| Host | 같은 IP의 어떤 이름을 요청했는가 | 서버·프록시 해석과 충돌 가능 |
| User-Agent | 클라이언트가 자신을 어떻게 표시했나 | 실제 실행 프로그램을 인증하지 않음 |
| Referer | 이전 자원에 대한 제공 정보 | 정책·직접 방문·앱 동작에 따라 누락 |
| Cookie | 상태·세션 연결 후보 | 비밀값 노출, 사용자 신원 보증 아님 |
| Accept 계열 | 허용·선호하는 표현 | q 가중치와 세부 규칙, 단순 첫 값 아님 |
| X-Forwarded-For | 프록시가 전달한 주소 후보 | 신뢰된 프록시 체인 밖 값은 위조 가능 |

클라이언트에서 임의로 X-Forwarded-For를 보낼 수도 있습니다. “헤더에 있으니 진짜 IP” 또는 “프록시 뒤에서만 존재”라고 단정하지 않습니다. 수신 시스템의 신뢰 설정과 연결 peer 주소를 확인합니다.

## 응답과 본문을 함께 읽기

N07은 200, text/plain, 36바이트 응답과 파일 해시를 제공합니다. 본문은 실행되지 않는 학습 문서입니다. Content-Type은 선언이며 실제 형식은 파일 바이트로 확인합니다. Server 헤더의 제품·버전도 생략·변경할 수 있어 확정된 자산 정보로 자동 등록하지 않습니다.

Content-Length는 메시지의 해당 콘텐츠 길이와 관련되며 압축 전 파일 크기·전체 네트워크 바이트량과 같지 않을 수 있습니다. HTTP/1.1의 chunked 전송은 콘텐츠 인코딩 gzip과 다른 층의 처리입니다. 재조립·전송 처리·콘텐츠 디코딩을 구별해야 객체 크기와 해시를 올바르게 계산합니다.

HEAD 응답은 GET에서 보낼 표현에 관련된 헤더를 줄 수 있지만 본문은 보내지 않습니다. 헤더에 길이가 있더라도 그 수만큼 객체가 전송되었다고 집계하지 않습니다. 캐시의 조건부 요청과 304도 새 본문 다운로드와 구별합니다.

## 거래별 결론 작성

T1의 302는 Location으로 이동하라는 응답입니다. T2가 실제로 이어졌는지는 별도 요청에서 확인합니다. T3의 202는 수락을 나타내지만 후속 처리는 자료에 없습니다. 보고서에서 요청 시도, 관측 응답, 업무 처리 완료를 같은 말로 쓰지 않습니다.

## 학습 활동

HTTP 텍스트에서 Host·Location·Content-Type·Content-Length를 표시하고 어떤 거래에 속하는지 적습니다. T3의 4096바이트 본문은 의도적으로 빠져 있으므로 어떤 문서가 업로드되었는지는 이 파일만으로 알 수 없습니다. 없는 본문을 추측해 복원하지 않습니다.
