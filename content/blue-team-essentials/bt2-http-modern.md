## 같은 HTTP 의미, 다른 전송 구조

메서드·상태·헤더·자원의 의미는 HTTP 버전 간에도 이어집니다. 다만 전송 구조가 다릅니다. HTTP/1.1의 텍스트 요청처럼 모든 패킷을 문자열 검색만으로 해석할 수 있다고 기대하면 HTTP/2·3에서 중요한 거래를 놓칠 수 있습니다. 실제 프로토콜 해석과 복호화 여부를 확인합니다.

| 버전 | 구조의 핵심 | 조사 단위 |
| --- | --- | --- |
| HTTP/1.1 | 요청·응답 메시지 | 연결 안의 각각의 거래 |
| HTTP/2 | TCP 연결의 바이너리 프레임·다중 스트림 | 스트림 ID·헤더·데이터 관계 |
| HTTP/3 | QUIC의 스트림 위에서 HTTP 전달 | QUIC 연결·HTTP 스트림·복호화 상태 |

## HTTP/2에서 바뀌는 읽기 방식

한 TCP 연결에 여러 요청과 응답이 교차할 수 있습니다. 연결 하나를 페이지 하나 또는 파일 하나로 집계하지 않습니다. HTTP/2의 :method·:scheme·:authority·:path 같은 pseudo-header가 전통적인 요청 줄·Host에 대응하는 정보를 표현합니다. 헤더 압축 때문에 패킷 하나의 바이트만 읽어 전체 헤더를 복원하기 어려울 수 있습니다.

로그가 제공하는 거래 식별자와 스트림 정보를 이용하고, PCAP 분석에서는 전체 연결·프레임 상태가 필요한지 검토합니다. 중간부터 수집하거나 패킷이 빠지면 암호화 외에도 해석이 불완전할 수 있습니다. 이때 없는 값은 “없음”과 “복원 불가”를 구별해 기록합니다.

## QUIC는 UDP 위에서도 연결 상태를 갖는다

QUIC는 UDP를 사용하지만 신뢰성·흐름 제어·암호화·연결 관리 기능을 제공합니다. HTTP/3는 단순히 HTTP/2의 바이트를 UDP에 옮긴 방식이 아닙니다. QUIC 자체도 HTTP/3 외의 용도로 쓰일 수 있습니다. UDP/443을 모두 HTTP/3로 단정하지 않고 프로토콜 해석이나 서비스 구성을 확인합니다.

QUIC의 연결 ID와 주소 변경 기능 때문에 IP·포트 묶음만으로 모든 연결 관계를 설명하기 어려운 경우가 있습니다. 제품이 제공하는 연결 식별과 관측 시각을 함께 살펴봅니다. 초기 패킷에서 얻을 수 있는 메타데이터가 전체 애플리케이션 본문을 복호화했다는 뜻은 아닙니다.

## 관측과 처리의 위치

수동 Sensor에서는 패킷 크기·시각·주소·일부 프로토콜 특성 정도만 얻는 상황이 있을 수 있습니다. 승인된 TLS 종료 프록시, 서비스 접근 로그와 앱 감사는 다른 관측 지점을 제공합니다. 각 도구가 해당 버전을 지원하는지, 해당 로그가 활성화되어 있는지 확인합니다. “Wireshark가 2022년에 못 읽었다”는 설명을 모든 현재 버전의 한계로 옮기지 않습니다.

이 조사 환경에서 단말 앱·프로세스 증거는 상시 네트워크 색인의 일부가 아닙니다. 필요하면 Hunt로 수집합니다. QUIC 흐름 N19에서 실제 앱이 무엇인지 확인하려면 앱 정책·서비스 자료 또는 단말 자료가 추가로 필요합니다.

## 가상 자료의 해석

N19는 12초 QUIC 흐름, 송수신 바이트와 메타데이터 제한을 나타냅니다. 세부 URL·HTTP 메서드·본문·ECH 평가가 없으므로 다운로드나 DoH를 확정할 수 없습니다. N05~N07의 HTTP 필드는 authorized_proxy 출처이고 N19는 tap-egress 출처입니다. 후자가 빈 필드를 가진 이유를 “앱이 필드를 숨겼다”로 바로 해석하지 않습니다.

## 학습 활동

한 연결에 GET 두 건과 POST 한 건이 존재할 수 있다는 예를 작성하고 연결 수와 요청 수를 구별합니다. N19에 대한 추가 자료 요청을 “URL·앱·사용자·시간 범위와 필요한 출처”로 구체화합니다. 제품 이름만 적은 요청보다 조사 질문이 명확해야 수집 범위를 줄일 수 있습니다.
