## 인코딩은 암호화가 아니다

Base64는 바이트를 문자로 표현하는 인코딩입니다. 키 없이 디코딩할 수 있어 비밀을 보호하지 않습니다. Base64url은 일부 문자를 URL에 적합하게 바꾼 형태이며 padding이 생략되는 경우도 있습니다. 끝에 =가 없다는 이유로 인코딩이 아니라고 판단하지 않습니다.

정상 쿠키·토큰·메일 첨부에서도 인코딩이 사용됩니다. URL percent encoding, Base64, gzip, TLS 암호화는 서로 다른 층입니다. 한 단계 해석 후의 바이트가 다시 압축·인코딩되었는지는 형식과 맥락을 보고 판단합니다. 알아볼 수 없는 문자열을 무조건 악성 명령이라고 부르지 않습니다.

~~~python
import base64
raw = base64.b64decode("aW52b2ljZS1sYWI=", validate=True)
print(raw.decode("ascii"))
~~~

기대 출력은 invoice-lab입니다. 고정된 무해 문자열을 디코딩하는 예이며 디코딩한 내용을 실행하지 않습니다. 실무에서는 원문·변환 단계·결과 바이트·사용 도구와 오류를 보존합니다.

## 객체 추출의 조건

| 조건 | 점검 이유 |
| --- | --- |
| 전체 요청·응답 연결 | 다른 거래의 본문을 섞지 않음 |
| 수집 길이·드롭 | 일부 객체를 전체로 취급하지 않음 |
| 복호화 가능 여부 | HTTPS 본문이 실제로 보이는지 |
| 전송·콘텐츠 인코딩 | chunked·gzip 등의 처리 구별 |
| 파일 형식·해시 | 선언·확장자 대신 실제 객체 확인 |
| 원본과 추출 기록 | 나중에 동일 분석을 재검토 |

Wireshark의 객체 내보내기는 도구가 해석한 거래와 수집 상태에 의존합니다. PCAP를 보관했어도 암호화 본문·손실·불완전 재조립 때문에 객체를 얻지 못할 수 있습니다. 추출 실패를 “파일이 없었다”로 해석하지 않습니다.

## 다운로드와 실행을 분리하기

N07에는 파일 응답과 해시가 있습니다. 학습 객체는 This is an inert training document.라는 무해 문서이며 악성 실행 파일이 아닙니다. HTTP 응답이 보였다는 것과 단말이 저장하고 실행했다는 것은 별도 사실입니다. 브라우저 다운로드 기록, 파일 흔적과 프로세스·Windows 이벤트를 필요 시 Hunt로 수집해야 합니다.

해시가 알려진 사례와 같다면 같은 바이트 객체를 연결하는 데 도움이 됩니다. 해시만으로 실행·행위자·업무 피해를 증명하지 않습니다. 파일 확장자가 .txt여도 실제 바이트 형식과 내부 구조는 별도로 살핍니다.

## 웹 공격의 시도와 성공

이례적인 입력, 알려진 취약점 패턴이나 WAF/IDS 경보는 공격 시도의 후보가 됩니다. 취약한 제품이 없거나 패치·검증·차단으로 실패했을 수 있습니다. 요청 문자열만 보고 취약점 실행을 확정하지 않습니다.

2022년 교재의 Log4Shell 요청·exploit kit 사례는 입력→서버 처리→후속 연결·파일·프로세스라는 확인 구조를 학습하는 데 사용합니다. 현재 조사에서는 실제 자산 버전·설정·패치와 서비스 감사를 확인합니다. 응답 200도 페이지 또는 오류 설명을 반환한 것일 수 있어 취약점 성공을 뜻하지 않습니다.

서버의 예상 밖 외부 연결은 후속 동작 후보이고, 원인 프로세스·계정·실행·변경 결과를 더 확인합니다. 요청 차단 여부, 앱 처리 결과와 사건 영향은 각각의 증거를 제시해야 합니다.
