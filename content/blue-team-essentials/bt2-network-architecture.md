## 구조를 알아야 통신을 해석할 수 있는 이유

같은 목적지 주소라도 센서가 내부, 방화벽 바깥, 프록시 뒤에 있으면 출발 주소와 읽을 수 있는 내용이 다릅니다. 사고 조사에서는 패킷의 출발·목적뿐 아니라 어떤 경로와 영역에서 관찰했는지 설명해야 합니다.

## 영역과 장비의 역할

| 요소 | 하는 일 | 분석에 필요한 질문 |
| --- | --- | --- |
| 스위치 | 같은 링크·VLAN의 프레임 전달 | 어떤 포트·VLAN을 복제하는가 |
| VLAN | 논리적으로 브로드캐스트 영역 분리 | 영역 사이 통신을 누가 라우팅하는가 |
| 라우터 | 다른 IP 네트워크로 전달 | 실제 경로·우회·비대칭은 무엇인가 |
| 방화벽 | 설정된 정책으로 통신 허용·차단 | 규칙·NAT·로그·방향이 맞는가 |
| DMZ | 외부 제공 서비스의 구역 | 내부 중요 자산으로의 경로는 제한됐는가 |
| 프록시·게이트웨이 | 연결 중계·인증·정책 | 실제 사용자의 대응 정보가 남는가 |

VLAN을 만들었다고 모든 접근이 자동 차단되지는 않습니다. 라우팅·ACL·방화벽·호스트 정책과 실제 연결 결과를 함께 확인합니다. 자산이 같은 영역에 있어도 업무상 필요한 통신만 정의할 수 있습니다.

## SPAN과 TAP

SPAN은 스위치가 지정된 트래픽을 미러 포트로 복제하는 방식입니다. 설정 범위·포트 용량·부하 등에 따라 손실이나 일부 정보 누락이 있을 수 있습니다.

TAP은 설치 링크를 관찰합니다. 링크를 지나지 않는 동일 VLAN 내부·가상 스위치 내부 통신은 보이지 않을 수 있습니다. TAP도 센서 처리·병합·저장 용량을 포함한 전체 수집 경로에서 손실을 검토합니다.

## 방화벽과 제로 트러스트 관점

주소·포트 중심 통제와 애플리케이션·사용자 맥락의 통제는 자료와 판단 조건이 다릅니다. 암호화된 내용을 읽을 수 있는지도 검토합니다. 허용 로그는 해당 관측 지점의 정책 결과이며 사용자의 모든 행위를 승인했다는 의미가 아닙니다.

제로 트러스트는 단순히 VLAN을 많이 나누는 이름이 아닙니다. 자산 위치만으로 신뢰를 고정하지 않고 신원·장치·자원·접근 조건을 지속적으로 평가하는 관점입니다.

## 작은 활동 — 세 경로 설명하기

호스트 → 외부 웹, 호스트 → 같은 VLAN 서버, 원격 사용자 → VPN → 내부 서버의 경로를 적습니다. 각 경로에서 남는 센서·방화벽·호스트·서비스 자료를 표시합니다.

**완료 기준:** 관측 가능한 흐름과 공백, NAT·프록시 전후의 주소 변화를 설명합니다.

## 최신 보강과 실무 연결

IPv6·클라우드·SaaS·암호화 경로는 기존 영역 지도에 추가합니다. 현재 키트의 배선과 정상 시험은 [관측 지도](network-architecture-visibility.html)에서 수행합니다.
