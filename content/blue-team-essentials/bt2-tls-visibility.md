## HTTPS의 보안과 분석의 가시성

TLS는 전송 중 기밀성·무결성과 인증을 제공하도록 설계되었습니다. 유효한 인증서가 있다는 사실은 요청한 이름과 신뢰 체계의 확인에 도움이 되지만 웹 콘텐츠의 선의까지 보증하지 않습니다. 악성 운영자도 인증서를 받을 수 있고 정상 사이트의 개별 계정·파일이 악용될 수 있습니다.

수동 Sensor가 어떤 값을 볼 수 있는지는 TLS 버전·핸드셰이크·ECH·복호화 자료·센서 위치에 따라 다릅니다. “443을 캡처했으니 URL을 안다”는 전제부터 점검합니다.

## 버전과 자료별로 구별하기

| 자료·조건 | 기대할 수 있는 정보 | 제한 |
| --- | --- | --- |
| 일반 수동 Flow | 주소·포트·시각·규모 | URL·본문·사용자 앱 불명 |
| 일반 TLS 1.2 초기 관측 | 일부 핸드셰이크·인증서 단서 | 재개·누락 등 조건에 영향 |
| 일반 TLS 1.3 수동 관측 | 일부 초기 메타데이터 | 서버 인증서 메시지는 암호화 |
| ECH 사용 | 외부 ClientHello의 제한된 정보 | 실제 inner 이름을 직접 못 볼 수 있음 |
| 승인된 TLS 종료 자료 | 해당 구간 HTTP 의미·로그 | 우회·예외·지원 앱은 별도 |
| 승인된 세션 비밀값 | 해당 연결 복호화 가능성 | 프로토콜·도구·완전성 조건 필요 |

TLS 1.3의 일반적인 인증서 기반 연결에서 서버 인증서 개인키만으로 기록된 모든 세션을 복호화할 수 없습니다. 세션 비밀값과 적절한 패킷·도구가 필요합니다. 키 로그는 해당 세션의 비밀을 포함할 수 있어 접근을 제한하고 필요한 범위에서 다룹니다.

## ECH의 현재 위치

2022년 교재는 ECH를 다가오는 변화로 설명합니다. 2026년 3월 RFC 9849가 공개되었으므로 현재 콘텐츠에서는 표준화된 기능으로 설명합니다. 다만 표준 발행과 모든 앱·서비스의 실제 사용은 다릅니다. ECH는 실제 ClientHello의 SNI 등 정보를 보호하며 외부 이름·IP만으로 안쪽 서비스를 확정할 수 없습니다.

N20은 학습 자료에서 ECH가 관측된 상황으로 표시되며 inner_sni=unavailable입니다. N19는 ECH가 평가되지 않은 QUIC 흐름입니다. 둘을 같은 조건으로 취급하지 않습니다. 실무의 필드·제품 지원·관측 근거는 버전과 설정을 확인해야 합니다.

## 승인된 TLS 종료는 두 연결을 만든다

기업 프록시가 TLS를 종료해 검사하는 경우 클라이언트↔프록시와 프록시↔원 서버는 서로 다른 보안 연결입니다. 관리 신뢰 체계, 서버 인증서 검증, 예외 앱·민감 서비스와 키 보호가 필요합니다. 프록시 뒤의 수동 캡처를 보아도 다시 암호화된 내용이면 원문은 보이지 않습니다.

모든 서비스에 복호화를 적용할 수 있다고 가정하지 않습니다. 인증서 pinning, 관리하지 않는 장치, 프로토콜 지원과 정책 예외 등을 확인합니다. 승인된 서비스·리졸버 감사와 필요 시 단말 Hunt를 보완 자료로 사용합니다.

## 지문의 올바른 사용

JA3·JA4 같은 지문은 여러 핸드셰이크 특성을 묶어 클라이언트·연결 후보를 비교하는 방법입니다. 정상·악성 앱이 값을 공유할 수 있고 변경·우회도 가능합니다. 특정 지문은 “추가 확인할 이유”로 사용하며 프로세스·사용자·악성코드 이름의 확정 키로 쓰지 않습니다.

## 학습 활동

N05~N07은 프록시의 HTTP 필드, N20은 수동 TLS 메타데이터입니다. 자료 위치에 따라 왜 정보가 다른지 설명합니다. N20에 대응할 추가 요청으로 승인된 프록시·앱 로그, 자산·시간·접속 대상 확인을 적습니다. 가시성 공백 자체를 악성 판정으로 바꾸지 않습니다.
