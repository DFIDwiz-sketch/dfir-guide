## 목표와 준비물

메모리 사본에서 프로세스와 연결의 단서를 찾고 디스크·이벤트·네트워크 증거로 검증합니다. 승인된 메모리 이미지, 수집 기록과 SHA-256, 분석용 저장소 및 Volatility 3가 필요합니다. 이미지가 없으면 이 글을 조사 설계용으로 읽고 실제 결과를 만들어낸 것처럼 기록하지 않습니다.

메모리에는 민감한 데이터가 포함될 수 있으므로 원본·분석 사본과 접근 범위를 관리합니다. 수집 자체도 메모리를 변경하며 이미지의 형식·OS·수집 도구에 따라 관찰 범위가 달라집니다.

## 1단계 — 이미지의 출처와 무결성 확인하기

사건·증거 ID, 장비, OS, 수집 시작·종료 시각과 도구 버전을 적습니다. 파일 크기와 해시를 비교하고 사본에서 분석합니다. `memory.raw`는 예시 파일명이며 확장자가 이미지 형식을 보장하지 않습니다.

완전한 물리 메모리 이미지, 크래시 덤프와 특정 프로세스 덤프는 같은 자료가 아닙니다. 분석 도구가 해당 형식과 운영체제를 지원하는지 먼저 확인합니다.

## 2단계 — 도구 버전과 기본 정보 확인하기

아래는 Volatility 3 소스 체크아웃에서 `vol.py`를 사용하는 예시입니다. 패키지 설치 방식에서는 실행 명령이 다를 수 있습니다.

```bash
python vol.py --help
python vol.py -f memory.raw windows.info
```

분석한 이미지가 Windows일 때 Windows 플러그인을 사용합니다. 출력과 오류를 별도 파일에 남기고 OS 정보, 레이어·심볼 요구를 확인합니다. Volatility 2의 profile 지정 방식을 그대로 옮기지 않습니다.

**확인할 결과:** 지원되는 이미지로 기본 정보를 읽을 수 있어야 합니다. 필요한 심볼이 없거나 다운로드가 제한된 경우 이를 해결한 뒤 다음 결과를 해석합니다. 요구 사항 오류를 ‘의심 프로세스 없음’으로 처리하지 않습니다.

## 3단계 — 프로세스 목록과 부모 관계 만들기

```bash
python vol.py -f memory.raw windows.pslist
python vol.py -f memory.raw windows.pstree
python vol.py -f memory.raw windows.psscan
```

목록 기반 확인과 메모리 스캔은 관찰 방식이 다릅니다. 차이가 있다면 생성·종료 시각, 오프셋과 객체의 유효성을 조사합니다. 스캔 결과에만 보인다는 이유로 곧바로 숨겨진 악성 프로세스라고 판단하지 않습니다. 종료된 프로세스의 잔여 객체나 손상도 고려합니다.

**남길 결과:** PID·PPID·이름·시각·발견 방법·의심 이유와 가능한 정상 설명을 포함한 목록입니다.

## 4단계 — 명령행과 모듈 맥락 확인하기

```bash
python vol.py -f memory.raw windows.cmdline
python vol.py -f memory.raw windows.dlllist
```

설치한 버전의 플러그인 도움말에서 PID 필터 등 지원 옵션을 확인한 뒤 대상을 좁힙니다. 경로·명령행과 로드된 모듈을 디스크 사본, 서명·해시·정상 설치 정보와 비교합니다.

출력이 비거나 읽기 오류가 있다고 모두 은폐로 판단하지 않습니다. 페이지 누락, 프로세스 종료, 수집 형식과 접근 가능한 메모리 범위가 영향을 줄 수 있습니다. 문자열에 명령이 보이는 것과 실제 실행됐다는 사실도 구분합니다.

## 5단계 — 연결 흔적과 네트워크 자료 대조하기

```bash
python vol.py -f memory.raw windows.netscan
```

지원되는 이미지에서 주소·포트·상태·소유 프로세스 후보를 확인합니다. 메모리 스캔으로 발견한 객체가 수집 순간의 활성 연결만을 뜻하지는 않습니다. 프로세스 수명과 센서의 시간·5-tuple을 함께 비교합니다.

PCAP에서 동일 연결이 없으면 센서 위치, 저장 기간과 시계 오차를 확인합니다. 메모리나 패킷 중 하나만을 우선적으로 참이라고 놓고 다른 증거를 버리지 않습니다.

## 6단계 — 의심 메모리 영역을 추가 조사하기

실행 가능한 메모리, 비정상 모듈 경로, 코드와 프로세스 역할의 불일치 등은 추가 조사 후보입니다. JIT·브라우저·보안 소프트웨어 등 정상 실행에서도 특별한 메모리 패턴이 나타날 수 있습니다.

버전별 지원 플러그인으로 영역과 주변 맥락을 확인하고 필요하면 분석 사본을 별도 추출해 출처·해시를 기록합니다. 추출 파일을 실행하는 것은 별도 격리 분석 단계이며 이 기본 조사에 자동으로 포함하지 않습니다.

## 7단계 — 결론과 한계 작성하기

| 항목 | 남길 내용 |
| --- | --- |
| 이미지 | 출처, 수집 시각·방법, 크기·해시 |
| 분석 환경 | Volatility 버전, 명령, 심볼과 오류 |
| 관찰 | 프로세스·명령행·모듈·연결의 근거 |
| 교차 검증 | 이벤트·디스크·PCAP에서 일치·불일치한 점 |
| 판단 | 의심 이유, 정상 대안, 미확인 부분 |

**완료 기준:** 의심 프로세스 한 개를 서로 다른 증거로 설명하고, 수집·심볼·플러그인 문제와 실제 행동 부재를 구분할 수 있습니다. 다음은 [Windows 초기 조사](windows-triage.html)와 [악성코드 행동 분석](malware-behavior.html)입니다.
