## 메일 인증과 사건의 안전성을 구분하기

SPF·DKIM·DMARC는 중요한 도메인 인증 수단입니다. 그러나 인증 통과는 발신 계정이 침해되지 않았거나 내용이 안전하다는 뜻이 아닙니다. 2022년의 SMTP·헤더 기본기에 SaaS 감사·토큰 악용·메일 규칙·업무 확인을 추가합니다.

이 가이드의 가상 헤더와 로그는 교육용입니다. 실제 메일의 개인정보·토큰·업무 내용을 공개 검사 사이트에 올리기 전에 허용된 처리 범위를 확인합니다. 원본 .eml과 첨부·서비스 감사는 필요한 범위에서 보존합니다.

## 1단계 — 원본과 메시지 식별자 확보하기

원본 메일, 수신 시각·계정·테넌트, Message-ID와 서비스 고유 ID, 메일 추적 기록을 확보합니다. 전달받은 화면 캡처만으로 원본 경로와 헤더를 재구성하지 않습니다. Message-ID 자체는 조작되거나 중복될 수 있어 서비스 ID·시간·수신자도 함께 사용합니다.

첨부를 실행하거나 링크를 누르지 않고 원본과 분석 사본을 나눕니다. 네트워크 센서에는 SMTP STARTTLS 이후 본문이 안 보일 수 있고, 웹메일 HTTPS만 보일 수도 있습니다. 메일 서비스의 보존·추적·감사로 보강합니다.

## 2단계 — 발신 필드와 신뢰 경계 읽기

| 항목 | 의미 | 확인할 한계 |
| --- | --- | --- |
| From | 사용자가 보는 작성자 | 표시 이름·도메인 사칭 가능 |
| MAIL FROM / Return-Path | SMTP 봉투 발신·반송 경로 | 표시 발신과 다를 수 있음 |
| Reply-To | 회신 대상으로 지정한 주소 | 실제 업무 관계와 다를 수 있음 |
| Received | 각 서버가 추가한 전달 정보 | 신뢰 경계 밖에서는 위조 가능 |
| Authentication-Results | 수신 시스템의 인증 평가 | 신뢰하는 시스템이 만든 항목인지 확인 |
| DKIM-Signature | 서명 도메인 d=·selector s= 등 | 존재만으로 검증 성공을 뜻하지 않음 |

Received는 새 항목이 위에 붙습니다. **신뢰하는 수신 게이트웨이가 기록한 상단 구간부터** 확인하고, 신뢰 경계를 파악한 뒤 아래 → 위 순서로 전달 후보를 정리합니다. 가장 아래 항목을 무조건 최초 발신 IP로 믿지 않습니다. 메일 경로에 신뢰하지 않는 인증 결과가 섞일 수 있습니다.

## 3단계 — SPF·DKIM·DMARC 정렬 확인하기

SPF는 연결 IP와 봉투 발신 도메인의 허용 관계를 평가합니다. DKIM은 서명과 지정된 헤더·본문의 무결성을 검증합니다. DMARC는 **From 도메인과 정렬된 SPF 또는 DKIM 성공**을 사용합니다. 둘 다 성공할 필요는 없습니다.

relaxed 정렬과 strict 정렬은 다릅니다. strict는 도메인의 정확한 일치, relaxed는 규격에 따른 Organizational Domain 관계를 확인합니다. 단순히 모든 발신 주소가 같은 문자열인지 비교하지 않습니다.

| 관찰 | 해석 |
| --- | --- |
| SPF pass, From과 비정렬, DKIM fail | SPF pass만으로 DMARC pass가 아님 |
| SPF fail, From과 정렬된 DKIM pass | DMARC pass 가능 |
| DMARC pass | 해당 From 도메인의 사용 검증, 내용·개인 신원 보증 아님 |
| DMARC fail | 정책·전달·변경·실제 사칭 등 추가 검토 |
| p=none | 모니터링 정책, 해당 메일의 인증 성공을 의미하지 않음 |

p=reject도 수신 측 모든 시스템이 반드시 같은 처리를 한다는 보장은 아닙니다. 실제 수신 정책과 결과를 확인합니다.

## 4단계 — 2026년 표준과 전달 예외 확인하기

**2026년 5월 RFC 9989가 RFC 7489·9091을 대체**하고 보고 규격은 RFC 9990·9991로 분리됐습니다. 새 규격은 Organizational Domain 탐색에 DNS Tree Walk를 정의하고 예전 pct 태그를 제거하며 t 테스트 태그를 도입합니다. 기존 공급자·파서가 즉시 모두 새 방식으로 바뀌었다고 가정하지 않습니다.

운영 DNS를 바꾸기 전에 메일 공급자의 지원·현재 판정과 보고서 처리 결과를 확인합니다. 정상 발송원·하위 도메인·전달·메일링리스트를 검토하고 정책 적용 전후 도착률과 인증 결과를 비교합니다.

전달은 연결 IP를 바꾸거나 본문을 수정해 SPF/DKIM/DMARC 실패를 유발할 수 있습니다. ARC는 인증 평가의 전달 이력을 보존하는 수단입니다. 유효한 체인과 신뢰하는 sealer 정책을 확인하며 arc=pass를 내용의 안전 판정으로 사용하지 않습니다.

## 5단계 — 피싱 이후 신원과 메일 행동 조사하기

공식 2026년 9월 EvilTokens 분석은 device-code 피싱 이후 토큰 악용, 메일 유출·악성 규칙·장치 등록을 보고합니다. 이는 헤더 분석으로 종료할 수 없는 사례입니다. 합법적인 인증 페이지를 이용한 흐름도 사용자가 요청 의도를 오해하도록 유도될 수 있습니다.

| 확인 영역 | 요청할 증거 |
| --- | --- |
| 로그인·인증 흐름 | 계정·앱·IP·시각·device-code 여부·세션 정보 |
| 토큰 관련 활동 | 서비스·리소스 접근, 앱 권한·세션·장치 변경 |
| 메일 동작 | 읽기·검색·내보내기·SendAs·규칙·전달·삭제 |
| 사용자의 행동 | 실제 요청 여부·메일 열람·승인 인지 |
| 업무 영향 | 외부 전달 내용·수신자·송금 변경·별도 채널 확인 |

자료에서 device-code 로그인이 보인다는 사실만으로 피싱 성공을 확정하지 않습니다. 앱과 업무 필요성, 사용자 확인, 후속 행동과 정책을 비교합니다. DMARC pass인 거래처 계정에서 온 요청도 BEC 후보가 될 수 있습니다.

## 6단계 — 가상 메일과 로그로 연습하기

[가상 헤더 파일](downloads/network-day2-mail.eml)은 실제 발송·서명 없이 만든 비작동 예입니다. 신뢰하는 lab-gateway.example의 평가와 외부에서 공급된 항목을 구분합니다. 예에는 검증 가능한 DKIM 서명이 없으므로 pass 문자열을 직접 재검증한 결과로 기록하지 않습니다.

[통합 실습](network-capstone.html)에서 N005의 인증 평가 pass, N009의 device-code 로그인, N010의 외부 전달 규칙을 확인합니다. 동일 계정의 시간상 연속성은 있지만 메일이 원인이거나 토큰이 탈취됐다는 증거는 아직 없습니다.

**결과물:** 인증 평가·사용자 확인·후속 감사·업무 승인 여부를 나눈 조사표. 정상 규칙과 비교할 담당자를 적습니다.

## 7단계 — 대응과 빈 결과 처리하기

근거가 확인되면 원본·감사 보존 후 계정 담당과 세션·앱 권한·장치·메일 규칙·외부 전달 범위를 확인합니다. 비밀번호 변경 하나로 모든 세션·토큰·앱 권한이 즉시 해소된다고 가정하지 않습니다. 제공자 절차와 실제 조치 결과를 검증합니다.

메일 감사가 없으면 라이선스·보존·이벤트 유형·수집 권한·시간과 서비스 설정을 확인합니다. 추적 ID를 못 찾으면 Message-ID·수신자·시간을 조합하되 추정 일치를 명시합니다.

**완료 기준:** 원본·신뢰 경계·인증 결과·신원 행동·업무 영향·미확인 항목과 대응 담당을 기록합니다. [클라우드 계정·토큰 대응](cloud-identity-response.html), [사건 관리](case-management.html)로 이어갑니다.
