## 목표와 시작 조건

조사 전에 “이 통신을 어떤 자료에서 볼 수 있는가?”를 답합니다. 수동 TAP은 설치된 링크를 지나는 패킷을 복제하며, 다른 링크·호스트 내부·SaaS 서버 내부의 모든 행동을 보여주지 않습니다. 구성도와 최근 변경 기록을 준비합니다.

2022년 교재의 VLAN·라우팅·SPAN/TAP 기본기에 클라우드·IPv6·프록시와 신원 정보를 추가합니다. 실제 키트의 Sensor는 대상망 측 TAP, Core는 분석 측 스위치와 연결되고 각 영역에 인라인 방화벽이 있습니다. 방향·포트·관리망은 실제 배선과 설정으로 확인합니다.

## 1단계 — 물리 연결과 논리 영역 따로 적기

| 대상 | 적을 정보 | 확인 근거 |
| --- | --- | --- |
| TAP·Sensor | 관찰 링크, 송수신 방향, VLAN, 수집 NIC | 배선·인터페이스·정상 시험 |
| Core·분석 스위치 | 관리와 분석 경로, 수집 결과 유입 | 포트·라우팅·접근 정책 |
| 방화벽 | 통과 경로, NAT, 허용/차단, 로그 활성화 | 규칙과 실제 기록 |
| 호스트·서버 | 자산 ID, 주소, 계정, 업무 역할 | 자산 목록·DHCP·Hunt |
| DNS·프록시·VPN | 실제 종단, 클라이언트 대응 정보 | 서비스 설정과 원본 감사 |
| 클라우드·SaaS | 리소스·테넌트 ID, 수집 가능한 API | 계정 권한·로그 설정 |

PC가 Core 측에 연결됐다는 이유로 그 트래픽이 대상망 TAP을 통과한다고 가정하지 않습니다. 방화벽·라우터의 논리 구간과 물리 연결을 모두 표시합니다. 수동 TAP은 차단 장비가 아닙니다.

## 2단계 — 대표 흐름 다섯 개 그리기

1. 대상 호스트 → 내부 리졸버 → 외부 DNS.
2. 대상 호스트 → 프록시 또는 게이트웨이 → 외부 웹.
3. 같은 VLAN 호스트 → 파일 서버 또는 다른 호스트.
4. VPN 사용자 → 게이트웨이 → 내부 서버.
5. 클라우드 워크로드 → 같은 클라우드의 관리 서비스.

각 흐름마다 Sensor·방화벽·서비스 로그 중 남는 자료를 적습니다. 같은 스위치에서 끝나는 통신은 업링크 TAP을 지나지 않을 수 있습니다. VM 간 통신도 가상 스위치 안에서 끝날 수 있습니다.

**기대 결과:** 대표 흐름마다 최소 한 개의 검증 가능한 자료 또는 명시적인 관측 공백을 갖습니다.

## 3단계 — NAT와 프록시 전후 주소 연결하기

주소와 함께 시각·포트·프로토콜·관측 지점을 적습니다. NAT 바깥에서 동일 공인 주소가 보여도 같은 내부 장비는 아닐 수 있습니다. NAT 변환 기록에서 같은 시간의 내부/외부 포트 대응을 확인합니다. VPN은 로그인 계정·세션·할당 주소의 유효 기간을 붙입니다.

프록시가 대신 연결하면 Sensor의 originator가 업무 PC가 아닌 프록시일 수 있습니다. 프록시 요청 로그와 인증 ID를 연결합니다. HTTP의 X-Forwarded-For는 신뢰하는 프록시가 생성·정제한 조건에서 사용하며 외부 요청의 값을 그대로 장비 식별자로 삼지 않습니다.

**결과가 없으면:** 보존 종료, 시차, NAT 포트 재사용, 누락 로그를 검토합니다. 연결을 증명할 수 없으면 “외부에서 관찰된 주소”까지만 기록합니다.

## 4단계 — IPv6와 암호화 경로 확인하기

IPv4 정책과 별도로 IPv6 주소·라우팅·방화벽·센서 수집을 확인합니다. IPv6 주소의 문서용 예는 2001:db8::/32이며 주소가 바뀔 수 있으므로 자산 ID와 기간으로 연결합니다. 실제 IPv6 패킷이 캡처되고 검색 필드에 남는지 확인합니다.

DoH·DoT·DoQ, QUIC·HTTP/3, ECH와 VPN 터널은 센서가 읽을 수 있는 내용을 바꿉니다. 이를 악성의 증거로 취급하지 않습니다. [암호화 가시성](encrypted-network-visibility.html)과 서비스·호스트 감사로 필요한 질문을 다시 구성합니다.

## 5단계 — 정상 시험으로 관측 검증하기

권한 있는 시험 장비에서 정상 DNS 조회와 내부 웹 접속을 수행하고 UTC 시작·종료 시각을 기록합니다. Sensor 원본 → Zeek/Suricata/Arkime → Splunk 순서로 찾습니다. 이름·주소·시간을 비교하되 도구 간 ID가 같을 것으로 기대하지 않습니다.

| 결과 | 다음 확인 |
| --- | --- |
| 방화벽에는 있고 PCAP에는 없음 | TAP 경로·방향·필터·손실·보존 |
| PCAP에는 있고 프로토콜 로그에는 없음 | 분석기·암호화·지원·캡처 불완전 |
| 원본 로그에는 있고 Splunk에는 없음 | 전송·파서·인덱스·시간·권한 |
| 웹은 있고 DNS가 없음 | 캐시·리졸버 위치·암호화 DNS·수집 조건 |
| 클라우드 통신이 안 보임 | 로컬 TAP을 실제 지나는지, 클라우드 로그 제공 범위 |

## 6단계 — 공백과 보강 계획 기록하기

네트워크 자료는 상시 수집·색인을 유지하되 호스트는 현재 키트의 **Velociraptor Hunt로 필요 시 수집**합니다. Hunt 결과는 수집 시점의 현재 상태 또는 남아 있는 과거 자료입니다. 상시 호스트 스트림처럼 취급하지 않습니다.

AWS VPC Flow Logs 같은 클라우드 자료도 패킷 본문이나 모든 트래픽을 제공하지 않습니다. 로그 상태·집계 간격·제외 트래픽·인터페이스 범위를 제품 문서로 확인합니다. 별도로 관리 API·DNS 서비스·로드밸런서·SaaS 감사를 추가합니다.

**완료 기준:** 어떤 자산·기간·흐름을 볼 수 있는지, 보지 못하는 이유와 보강 담당을 한 페이지에 설명합니다. [관측 지도 운영](defensible-visibility.html), [수집 상태](telemetry-health.html), [수집과 증거](network-capture-evidence.html)로 이어갑니다.
