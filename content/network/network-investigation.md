## 센서가 무엇을 보고 있는가

분석 전에 TAP·SPAN의 위치, 수집 인터페이스, 패킷 손실과 저장 기간을 확인합니다. 인터넷 경계 센서가 내부의 모든 통신을 보여주는 것은 아닙니다. TLS·QUIC 등 암호화된 통신에서는 수동 패킷만으로 본문을 읽지 못할 수 있습니다.

## 데이터별 역할

| 자료 | 강점 | 확인할 한계 |
| --- | --- | --- |
| PCAP | 패킷과 실제 프로토콜 교환 검토 | 저장 누락, 암호화와 패킷 손실 |
| Zeek 로그 | 연결·DNS·HTTP 등 구조화된 맥락 | 파서·설정·센서 범위에 의존 |
| Suricata 경보 | 규칙에 맞는 행위의 조사 출발점 | 규칙 범위와 오탐 |
| Arkime 세션 | 인덱스 검색 후 패킷으로 이동 | 메타데이터만 보존될 수도 있음 |
| 호스트 로그 | 계정·프로세스와 통신 연결 | 사전 수집·감사 설정 필요 |

## 조사 순서

1. 의심 시각, 출발지·목적지, 포트와 프로토콜을 고정합니다.
2. 같은 통신의 연결 로그·경보·세션을 찾아 비교합니다.
3. DNS 이름, HTTP 요청 또는 TLS 메타데이터를 연결합니다.
4. 원본 패킷을 볼 수 있다면 프로토콜과 응답을 확인합니다.
5. 호스트의 프로세스·계정·파일 기록으로 원인과 결과를 조사합니다.
6. 다른 장비·계정·시간대의 관련 행위를 찾아 범위를 넓힙니다.

서로 다른 도구의 식별자는 자동으로 같지 않습니다. Zeek의 `uid`와 Suricata의 `flow_id`를 같은 값으로 조인하지 말고 시간과 주소·포트·프로토콜을 대조합니다. NAT·프록시와 시계 오차도 확인합니다.

## 해석할 때 주의할 점

HTTP 요청이 존재한다는 사실과 서버에서 코드가 실행됐다는 사실은 다릅니다. 큰 데이터 전송도 승인된 백업·동기화와 비교해야 합니다. 경보 하나가 아닌 요청·응답·후속 통신·호스트의 실행을 함께 봅니다.
