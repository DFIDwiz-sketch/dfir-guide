## 이 가이드의 목표와 준비물

수집한 파일을 재확인할 수 있도록 보존하고, 서로 다른 로그의 시간을 비교하는 것이 목표입니다. 분석용 PC, 수집 파일의 사본, 별도의 증거 저장 위치와 기록 양식을 준비합니다. 아래 폴더와 사건 번호는 예시입니다.

## 1단계 — 사건 폴더와 증거 목록 만들기

분석용 저장소에 `CASE-001`을 만들고 `originals`, `working`, `notes`, `exports` 폴더로 나눕니다. 이 폴더 구조만으로 읽기 전용이나 접근 통제가 구현되지는 않습니다. 원본 폴더의 쓰기 권한·보관·백업은 운영 절차에 맞춰 관리합니다.

| 필수 항목 | 적을 내용 |
| --- | --- |
| 증거 ID | EVID-001처럼 중복되지 않는 번호 |
| 출처 | 장비 식별자, 로그 채널 또는 원래 파일 경로 |
| 수집 시각 | UTC 또는 오프셋을 포함한 시각 |
| 방법 | 도구·버전·명령·계정 권한 |
| 수집 결과 | 성공·부분 성공·실패와 누락 범위 |
| 무결성·보관 | 파일 크기, SHA-256, 저장 위치와 인계 기록 |

**확인할 결과:** 같은 이름의 `Security.evtx`가 여러 장비에서 와도 서로 구분할 수 있어야 합니다. 파일 이름만 바꾸고 원래 경로를 잃어버리지 않도록 합니다.

## 2단계 — 수집 파일의 해시 계산하기

Windows 분석 PC의 PowerShell에서 예시 파일의 해시를 확인합니다. 경로는 실제 보관 위치로 바꿉니다.

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath .\CASE-001\originals\LAB-FS01-Security.evtx |
  Export-Csv .\CASE-001\notes\hashes.csv -NoTypeInformation -Encoding UTF8
```

Linux 분석 PC에서는 다음처럼 실행할 수 있습니다.

```bash
sha256sum CASE-001/originals/LAB-FS01-Security.evtx > CASE-001/notes/hashes.sha256
```

**확인할 결과:** SHA-256 값은 16진수 64자리입니다. 파일 접근 오류나 잘못된 경로가 있으면 정상 해시로 기록하지 않습니다. 서로 다른 도구가 같은 파일 바이트를 읽었다면 같은 알고리즘의 해시값은 같아야 합니다.

## 3단계 — 분석 사본을 만들고 복사 결과 확인하기

원본에서 `working` 폴더로 복사한 뒤 원본과 사본의 해시를 비교합니다. 아래는 기존 파일을 덮어쓰지 않도록 처음 만드는 사본에 사용하는 예시입니다.

```powershell
$sourceFile = '.\CASE-001\originals\LAB-FS01-Security.evtx'
$workingFile = '.\CASE-001\working\LAB-FS01-Security.evtx'
if (Test-Path -LiteralPath $workingFile) { throw '분석 사본이 이미 존재합니다.' }
Copy-Item -LiteralPath $sourceFile -Destination $workingFile
(Get-FileHash -Algorithm SHA256 -LiteralPath $sourceFile).Hash -eq
  (Get-FileHash -Algorithm SHA256 -LiteralPath $workingFile).Hash
```

결과가 `True`이면 비교 시점의 파일 바이트가 같습니다. `False`면 복사를 중단하고 경로·파일 변경·수집 완료 여부를 확인합니다. 분석 결과 CSV나 필터링한 PCAP은 별도의 파생 자료로 등록하며 원본과 같은 해시를 기대하지 않습니다.

## 4단계 — 네 종류의 시간을 분리하기

| 시간 | 뜻 | 예시 함정 |
| --- | --- | --- |
| 발생 시간 | 로그가 표현하는 행동 시각 | 장비 시계 오차 |
| 기록 시간 | 시스템이 로그에 기록한 시각 | 버퍼링과 애플리케이션 처리 지연 |
| 수집 시간 | 분석 도구가 자료를 확보한 시각 | 며칠 전 기록을 오늘 수집할 수 있음 |
| 색인 시간 | SIEM이 이벤트를 색인한 시각 | 과거 자료 재수집은 지연처럼 보일 수 있음 |

원문에는 시간대 정보가 있는지 먼저 확인합니다. UTC를 뜻하는 `Z`, `+11:00` 같은 오프셋, 시간대 없는 문자열을 구분합니다. 분석 화면의 표시 시간대가 원문 시간대와 같다는 보장은 없습니다.

## 5단계 — 타임라인을 작성하기

공통 비교 열은 UTC로 두되 원래 문자열도 남깁니다. 시계 오차가 확인돼 보정했다면 원문을 수정하지 말고 별도 보정 열에 값과 근거를 기록합니다.

| 비교 시각 UTC | 증거 ID·기록 ID | 장비 | 관찰된 행동 | 해석·한계 |
| --- | --- | --- | --- | --- |
| 2026-10-07T00:05:02Z | EVID-001 / E004 | LAB-FS01 | NTLM 네트워크 로그온 성공 | 인증 수단 악용 여부 미확인 |
| 2026-10-07T00:06:00Z | EVID-001 / E005 | LAB-FS01 | 예약 작업 생성 | 실제 실행 여부는 별도 확인 |

위 내용은 [가상 로그 실습](first-investigation.html)의 예시입니다. 수집 시각을 행동 시각으로 넣거나, 두 사건의 시간 순서를 곧바로 인과관계로 바꾸지 않습니다.

## 6단계 — 인계와 재검증하기

분석 결과에서 사용한 증거 ID, 도구 버전, 필터, 시간 범위를 남깁니다. 파일을 인계할 때 수신자가 해시를 다시 계산해 비교할 수 있도록 목록을 함께 전달합니다. “변경되지 않은 파일”과 “누락 없이 수집된 자료”는 서로 다른 검증 항목입니다.

**완료 기준:** 출처·수집 방법·원본/사본·해시·시간 변환·분석 결과가 연결되고, 다음 담당자가 동일한 사본으로 같은 필터를 실행할 수 있습니다.
