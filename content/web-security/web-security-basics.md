## HTTP의 흐름부터 읽기

요청 메서드·경로·헤더·쿠키·본문과 응답 상태·헤더·본문을 구분합니다. 사용자 인증과 해당 자원 접근의 권한 판단은 별개입니다. 웹 서버·앱·프록시·DB의 기록을 함께 보면 패킷만으로 보이지 않는 처리를 설명할 수 있습니다.

## 학습할 주제

| 주제 | 핵심 질문 |
| --- | --- |
| Authentication | 사용자의 신원을 어떻게 검증하는가 |
| Access control | 각 자원과 행동의 권한을 서버가 검사하는가 |
| SQL injection | 입력이 데이터와 쿼리 구조에서 어떻게 처리되는가 |
| XSS | 입력이 브라우저의 실행 문맥으로 들어가는가 |
| SSRF | 서버가 어떤 주소로 요청할 수 있는가 |
| File upload | 저장·검사·실행과 접근 정책이 어떻게 연결되는가 |

구체적인 학습과 재현에는 PortSwigger Web Security Academy의 주제별 설명과 제공 랩을 활용할 수 있습니다. 서비스는 무료로 제공되는 학습 자료와 실습 랩을 안내합니다.

## 공격과 방어를 함께 기록하기

실습에서 취약점의 원인, 처리된 입력과 결과를 설명합니다. 웹 요청·서버 로그·프로세스·파일·DB·네트워크에서 남는 자료를 비교하고 예방 설정과 탐지의 차이를 정리합니다.

## 웹셸 조사 예시 관점

업로드 요청 하나로 코드 실행을 확정하지 않습니다. 저장된 파일 내용, 이후 접근 요청, 웹 프로세스의 자식 실행과 통신을 연결합니다. 확장자·응답 코드·IDS 경보 각각의 증명 범위를 구분합니다.

## API·세션·클라우드 연동으로 확장하기

브라우저 화면에서 버튼을 숨기는 것과 서버의 권한 검사는 다릅니다. API는 요청 주체·대상 객체·수행 기능별 권한을 서버에서 판단해야 합니다. 자기 시험 계정과 랩의 자원으로 정상 권한과 거부 결과를 비교하고, 다른 사용자의 운영 자료를 조회해 시험하지 않습니다.

클라우드 연동에서는 웹 로그인 성공 이후 앱 권한·토큰·세션을 함께 봅니다. SSRF는 서버가 요청한 목적지와 해당 실행 환경의 신원·권한까지 영향을 줄 수 있어 외부 요청 로그와 클라우드 감사를 연결합니다. 입력 필터 하나만으로 전체 접근 정책을 대신하지 않습니다. [클라우드 인증 조사](cloud-identity-response.html), [클라우드 워크로드](cloud-container-forensics.html).

## 파일 업로드 사건을 조사하는 6단계

1. 요청 ID·시각·계정·업로드 경로·응답을 보존합니다. 200 응답은 실행 성공을 의미하지 않습니다.
2. 서버에 저장된 파일의 실제 형식·내용·해시·소유자·시간을 읽기 방식으로 확인합니다.
3. 웹 서버와 앱의 경로 매핑·실행 설정·접근 권한을 확인합니다. 확장자만으로 실행 가능성을 결정하지 않습니다.
4. 저장 이후 요청, 웹 프로세스의 자식 실행, 파일 변경과 외부 통신을 연결합니다.
5. 동일 계정·요청 경로·파일 내용·행동으로 범위를 넓히고 정상 업로드와 비교합니다.
6. 원인 수정과 함께 이미 실행된 코드·노출 계정·지속 접근을 조사하고 검증합니다.

저장 위치 분리, 실행 금지, 파일명·크기·형식 검증과 서버 측 권한 판단은 서로 보완합니다. 백신 검사나 확장자 허용 목록 하나가 전체 업로드 보안은 아닙니다. [PortSwigger 공식 업로드 설명](https://portswigger.net/web-security/file-upload)을 원리 학습에 사용합니다.
